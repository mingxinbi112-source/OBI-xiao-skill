# 从现场到钱箱:FDE 产品化 Playbook

> 来源:一个行业人(美业)用 FDE 思路,从一段获得授权的服务录音出发,跑到 10+ 家门店按 500 元/店付费内测、20+ 家预约年费 9800 元正式版的全过程方法论。
> 与 SKILL.md 四阶段的关系:四阶段回答**"签约后怎么把项目工程化做下去、不死"**;本 Playbook 回答更上游和更下游的两件事——**"怎么从现场找到真问题、验证有人愿意付费"** 和 **"怎么把多次交付沉淀成产品,下一次不从零开始"**。
> 一句话:**FDE = 从现场到钱箱的脏活闭环**。你得扎到客户干活的一线(现场),找到他真正头疼的繁琐问题(脏活),做出能帮他解决问题的东西,并最终让他愿意为结果付钱(钱箱),从头到尾一步都不能断(闭环)。

> 🔗 **上游约束(别让链路跑空):** 本 Playbook 的 step 3-4「定义范围 / 共同搭建」把真问题压成最小闭环,这个最小闭环的**签约前验证工具**(影子工作法 + MVD 三军规)见 `pre-signing-audit-toolkit.md` Day3.5——先用影子工作法跟真人做一天、看清真实工作流,再用 MVD(Minimum Viable Deployment)三军规把范围逼到"两周内能验证"的最小单元,然后本 Playbook 才接得上把该单元做到能付费。**跳过上游验证直接做产品,等于在没确认真问题的情况下烧交付预算。** 本 Playbook(0→1 产品验证视角)与企业级签约交付四阶段(乙方工程化视角)的对齐,见下文「七步责任链 ↔ 四阶段映射」。

## 1. 三个乘法公式:全程诊断器

三个公式不是为了显得专业,而是**诊断卡在哪一环**——任何一项接近零,最后价值就接近零。项目卡住时,逐项排查哪一乘项塌了。

### ① FDE 结果 = 真问题 × 可用结果 × 进入工作 × 持续使用

| 乘项 | 含义 | 塌了的表现 |
|---|---|---|
| **真问题** | 现实里反复发生,已让人损失时间/金钱/机会 | 做完了没人用,因为问题不真 |
| **可用结果** | 人能核对,看完知道下一步做什么 | 结果是一堆正确废话,无法行动 |
| **进入工作** | 结果在正确时刻交到真正要做决定的人手里 | 结果躺在邮箱/群里,没进业务流 |
| **持续使用** | 用户之后还会用、会改、会提供新材料 | 打开一次就关,没有第二次 |

### ② 采用 = 看得懂 × 信得过 × 不麻烦 × 有下一步

客户不用时,别先怪"他们不懂 AI""员工执行力不行"。先反过来查是不是把麻烦都留给了客户:
- **看得懂**:使用者一眼知道这份结果在说什么;
- **信得过**:关键判断能回到原始材料和业务依据;
- **不麻烦**:不要求用户反复搬运、填写、解释;
- **有下一步**:看完马上知道该做哪一个动作。

> 想让员工多用,第一反应不该是再安排一场培训,而是先把产品做得更简单。培训能帮人理解,但不能用培训掩盖产品本身复杂。**采用不是要求员工"以后多用",而是把每一次使用的成本降到足够低。**

### ③ 真需求证据 = 具体角色 × 最近事件 × 当前做法 × 明确后果 × 真实材料 × 付费角色

只要有一项说不清,就先别急着做功能,回去补一份真实证据。这个公式是阶段一「真需求卡」的内核,也是和「客户说想要」划清界线的工具——**"客户说想要"是解决办法,不是需求成立的证据**。

## 2. 七步责任链 + 七个过关信号

七步不用一上来背,先看成三段;每走一步,只要拿到一个能继续往下的**证据**(不是一份材料)。

### 三段视图

| 段 | 步骤 | 解决 |
|---|---|---|
| 做之前,先看清问题 | 进入现场 → 发现问题 → 定义范围 | 这次到底做不做、做哪一段 |
| 交付时,把结果接进工作 | 共同搭建 → 部署工作流 | 结果怎么进入真实业务 |
| 用过以后,再判断价值 | 促进采用 → 验证影响 | 这次有没有人用、证明了什么 |
| (再绕一圈) | 现场反过来改产品 | 下一次能不能更快更稳 |

### 七步与过关信号

| 步 | 过关信号(拿到这个证据才算过) |
|---|---|
| 1. 进入现场 | 能说清最近一次事情怎么发生,并拿到一份合规、获授权的真实材料 |
| 2. 发现问题 | 能说清谁在什么环节卡住、已损失什么、现在用什么笨办法补救 |
| 3. 定义范围 | 第一版只有一个用户/一个输入/一个结果/一个下一步,且说清这次不做什么 |
| 4. 共同搭建 | 业务方把标准、样本、判断放进来,结果好不好有真人可核对 |
| 5. 部署工作流 | 先确定结果在什么时刻交给谁、他接下来做什么(不一定是技术部署) |
| 6. 促进采用 | 用户看得懂、信得过、用起来不麻烦,且知道拿到结果后往哪走 |
| 7. 验证影响 | 记录真实行为——谁用了、改了什么、是否再次提供材料或付费(不是一句"挺厉害") |

> **哪一步没有证据,就先回到那一步补,不要靠继续加功能把问题盖过去。**

### 两条闭环(缺一不可)

- **客户现场闭环**(解决"这一次有没有用"):真实材料 → AI 处理 → 可用结果 → 下一步动作 → 使用反馈
- **产品反馈闭环**(解决"下一次能不能更快更稳"):使用反馈 → 比较重复与例外 → 沉淀最小能力 → 放进下一次交付

只跑第一条,每来一家客户都从头重做,经验只长在交付者身上;只跑第二条,团队就关在房间里研究"用户应该需要什么"。FDE 既不是无限定制,也不是闭门造产品。

> 七步与四阶段的映射见 SKILL.md「七步责任链 ↔ 四阶段映射表」。

## 3. 进入现场:从业务流程里找到真问题

### 现场不是地点,客户也不是一个人

**现场**不是"必须去线下",而是一件真实业务正在发生、有人做判断、有人承担结果的工作链:
- 美业现场:咨询 → 到店 → 服务沟通 → 成交 → 回访 → 复购
- 电商现场:选品 → 投放 → 客服 → 履约 → 退款 → 复购
- 内容现场:选题 → 生产 → 发布 → 数据反馈 → 下一轮调整

判断有没有进入现场,不看地点,看三件事(三件都能做到,即使全程在线也在现场):
1. 能不能看到最近一次真实事件?
2. 能不能拿到一份合规、获授权的材料?
3. 结果出来以后,能不能继续追到下一步?

### 把一句含糊的"客户"拆成四种角色

分不清这四种人,就不知道谁该提供材料、谁核对结果、谁执行下一步、为什么有人愿意付钱。

| 角色 | 服务录音场景里是谁 |
|---|---|
| **使用者** | 提交材料、查看结果的美容师/店长 |
| **受益者** | 希望下次服务能接住自己顾虑的顾客 |
| **决策者** | 能让这件事进入日常工作的店长/业务负责人 |
| **付费者** | 最后判断是否值得持续投入的老板 |

> 这四个人不一定是同一个。和阶段二「专家类型诊断」配合:使用者往往是隐性知识持有者,付费者往往是阶段一成功标准的拍板人。

### 先把原来的工作摊开,再排序

普通人做 AI 产品的最大优势不是更懂技术,而是更熟悉一条真实业务。先把完整流程摊开(画流程图不是为了每个节点都做产品,恰恰相反——为了忍住"哪里都能做"的冲动),再用六角度给问题排序:

1. **频次**:多久发生一次?
2. **耗时**:每次投入多少人力?
3. **错误率**:现在最容易在哪里做坏?
4. **收入影响**:离成交/复购/成本有多近?
5. **个人依赖**:是不是只有少数人凭经验才能做好?
6. **AI 适配度**:有没有材料、判断标准和可检查的结果?

### 别听观点,追问最近一次到底发生了什么

客户开口常带着产品答案:"我想要录音""我想做行业 Agent""把整套流程自动化"。这些话要听,但不能照着做——它们是此刻想到的**解决办法**,不是需求成立的证据。把话题拉回五个问题:

1. **谁遇到?** 使用者/受益者/决策者/付费者分别是谁?
2. **什么时候发生?** 最近一次具体事件在流程哪一步?
3. **现在怎么办?** 对方正靠人、表格、聊天还是经验绕过去?
4. **不解决会损失什么?** 时间、人力、收入、机会、体验还是信任?
5. **能拿到什么?** 有没有获授权、可脱敏的录音、聊天、表格、订单、操作记录?

最后补两句:这件事多久发生一次?为了绕过去,对方已投入多少时间/人力/钱?

### 真需求卡七项(必须具体)

1. **具体角色**:谁遇到、谁使用、谁受益、谁决定、谁付费?
2. **最近事件**:哪一天、哪一步、具体发生了什么?
3. **当前做法**:现在怎样绕过去,为什么仍然不够?
4. **明确后果**:不解决会损失什么?
5. **已有投入**:已投入哪些时间、人力、流程、数据或钱?
6. **真实材料**:能拿出哪一份获授权、可脱敏的材料?
7. **下一次验证**:七天内只做哪一个动作补证据?

### 真需求过滤三原则

- 只有观点,没有事件 → 先不过;
- 只有痛点,没有后果 → 先不过;
- 只有想法,拿不到材料 → 先不过。

不是方向一定错,而是现在还不值得急着做。

## 4. 定义范围与共同搭建:把真问题压成一个小闭环

### 做窄:一个现场 20-30 节点,第一版只抓最关键的 1-2 个

"做窄"不是少做几个页面,而是先把一整个真实现场拆开,再决定第一版只解决哪一小段。筛选只看四件事:

1. **发生得够频繁**:一再出现,不是偶发;
2. **后果够具体**:真影响服务/判断/成交/培训/交付;
3. **有真实材料**:能拿到录音/聊天/表格/照片/操作记录;
4. **能很快拿到反馈**:做出结果后有人马上使用、核对或拒绝。

> 如果两个节点属于两条完全不同的问题链,材料、使用者和验收方式都不同,就不要因为都重要而一起塞进第一版。**第一版最好只抓一个;最多两个,但必须能被同一份核心材料和同一轮验证串起来。**

### 做深:最小闭环五步链

"窄"解决范围,"深"解决价值。节点选少了不等于做浅,反而要把这个节点从真实输入做到账面可核对、工作里可使用:

| 步 | 服务录音里的例子 |
|---|---|
| 真实输入 | 一段获得授权、完成脱敏的服务记录 |
| AI 一步 | 对照门店资料,找出顾客顾虑、员工回应和遗漏 |
| 可用结果 | 一份店长能逐条核对的复盘 |
| 下一动作 | 只挑一条进入顾客跟进或员工训练 |
| 反馈信号 | 记录店长和美容师采用了、修改了还是放弃了 |

> 最容易犯的错:把"录音上传成功"当闭环开始,把"报告生成完成"当闭环结束。录音只是输入,报告只是中间结果。**真正闭合的信号,是一个真实的人愿意拿着这份结果,把选中的节点继续往前推进。**

### 共同搭建:业务方至少交四样东西

小闭环能不能跑起来,不能只靠技术一边猜。业务方也要下场:

- **真实材料**:获授权、脱敏的录音/聊天/表格/操作记录;
- **判断标准**:项目知识、服务规范、风险边界、优秀样例;
- **验收角色**:谁最懂这件事、谁有权判断结果能不能用;
- **下一动作**:结果在什么时刻交给谁、他接下来做什么。

技术负责把材料/标准/流程变成 AI 能处理、真人能检查的结果;业务负责把现场真正的判断放进来,并对结果说"对、错、哪里要改"。少了业务材料,AI 只能给通用答案;少了技术实现,经验只留在少数人脑子里。这和阶段二「抢救隐性知识」是同一件事的两面。

### 可核对结果:让店长看见四件事

一份可核对的复盘,至少要让验收角色看见:
1. 顾客(原始对象)原来怎么说;
2. 员工当时怎么回应;
3. AI 为什么作出这个判断(依据);
4. 下一次可以怎样改。

> 分数只是入口。没有原始材料,验收人没法核;没有判断依据,验收人不敢信;没有下一次建议,报告看完就被关掉。

### Demo 到小闭环的五个变化

Demo 只是容器。从"展示功能"跨到"小闭环",至少发生五个变化:
1. 从虚构案例 → 客户授权、脱敏的真实材料;
2. 从只看页面 → 同时看见输入、判断依据和结果;
3. 从"你觉得怎么样" → 让一个真实角色拿走结果做下一步;
4. 从记录称赞 → 记录采用、修改、拒绝或继续提供材料;
5. 从演示完继续扩节点 → 根据反馈决定把当前节点做深、修改、停止,还是进入下一个相邻节点。

> 页面能打开只证明载体存在;客户愿意拿结果继续做事,闭环才真正开始转动。

### 关键节点卡(开工前写一页纸)

1. 现场边界:这次只研究哪一段真实工作;
2. 现场节点:这一段从开始到结束有哪些节点;
3. 问题节点:哪五六个节点反复出问题,各有什么证据;
4. 首版节点:第一版只选哪一个,最多哪两个同链节点;
5. 入选理由:为什么它比其他节点更高频、更痛、更有材料、更快得到反馈;
6. 节点输入:哪一份已授权、已脱敏的真实材料进入这里;
7. 节点结果:用户最终拿走什么,怎样核对;
8. 下一动作:结果进入哪个紧邻的工作节点;
9. 反馈与停止:什么行为说明继续做深,什么情况说明应暂停。

> 如果第一版同时出现多套互不相关的使用者、输入、结果和下一动作,说明范围还没真正做窄。继续往下收,直到一份核心材料只穿过一条最短价值链。

## 5. 让结果进入工作并被采用

### 别先讲怎么做,先把结果拿出来

老板不关心你用什么工具,关心的是:**你到底能帮我解决什么问题,我最后能拿到什么结果?** 第一次见客户,不要先说"我要给你做个什么东西"。直接拿他正在发生的问题,做出一份结果给他看。

"看到了结果" ≠ "结果被用起来",分界线很简单:
- 老板看完说"挺厉害" = 只是看到了结果;
- 店长从结果里挑出一条顾虑,放进下一次跟进 = 采用才开始;
- 店长挑出一段员工没接住的话,放进下一次训练 = 采用才开始。

对老板只需说清四件事:谁拿到结果 / 什么时候拿到 / 能看清什么 / 看完马上做哪一个动作。

### 采用诊断:四道门排查表

| 门 | 检查 |
|---|---|
| 看得懂 | 使用者一眼知道这份结果在说什么 |
| 信得过 | 关键判断能回到原始材料和业务依据 |
| 不麻烦 | 不要求反复搬运、填写、解释 |
| 有下一步 | 看完马上知道该做哪一个动作 |

常见阻碍:输入材料难采集 / 授权隐私让人不安心 / 结果太长当下用不上 / 判断依据看不见不敢信 / 每次要重新登录搬运 / 看完不知道下一步做什么。
具体先查四件:能不能只保留一个入口 / 能不能少点一个按钮 / 能不能不重复填写搬运 / 能不能一眼看懂并马上知道下一步。

> 真正好用的感觉像第一次拿到 iPad:不用先读说明书,看到就懂,点一下就能用。

### 不问"好不好",看接下来做了什么

一句"挺好的"可能是真认可,也可能只是礼貌。更可靠的判断是看客户愿不愿意承担越来越真实的成本——这就是**商业证据阶梯**,见下一节。

### 商业证据阶梯(七层,不能跨级庆祝)

```
称赞("挺厉害")              ← 1. 最弱,礼貌可能占大头
  ↓
愿意继续聊
  ↓
愿意提供一份真实材料          ← 信任成本
  ↓
愿意让一个真实用户使用        ← 组织成本
  ↓
愿意支付第一次费用            ← 金钱成本
  ↓
愿意复购、扩展或介绍同行      ← 价值不是只出现一次
  ↓
出现可以核验的经营改善        ← 还需基线、周期、归因口径
```

**证据越往上,客户承担的成本越高。** 最容易犯的错是**跨级替自己庆祝**:愿意给材料 ≠ 已采用;使用过一次 ≠ 持续使用;付过一次钱 ≠ 已续费,更 ≠ 经营结果已提升。

> 收过钱,只能证明当下有人愿意买;结果反复进入工作、客户继续使用、价值随使用积累,才有机会长成持续产品。这是阶段四「预期管理」之外,另一条贯穿全程的验证标尺——它回答的不是"客户满不满意",而是"客户说好到底证明了什么"。

> 🔗 **正交澄清(证据成型 vs 收费控制,别混):** 本阶梯是**证据成型视角**——客户承担的成本递增,证明价值在累积(用于判断"现在到底证明了什么")。它**不回答"在哪个环节收钱、怎么从免费转付费"**——那是收费控制点视角,见 `renewal-and-expansion-playbook.md`「免费午餐终结五开关」。两者正交:商业证据阶梯管"证据怎么一层层沉淀",五开关管"在哪个价值兑现点设收费闸"。**先有证据阶梯确认价值成立,再在阶梯的某一层设收费开关**——证据没到那层就收费 = 杀鸡取卵,证据到了却不设开关 = 永远免费午餐。

### 反面教材:收过钱却没长成产品(小红书内容项目)

一个内容生成项目也收过钱:原来一篇内容要自己想选题、写文案、找图,现在输入关键词就能拿到完整图文,省时间立刻看得见。问题出在两三个月后:客户学会了操作,继续找你交付的必要性变弱;而当时只证明了"内容可以更快生成",没追三件更难的事:
1. 发出去以后,有没有带来更多真实咨询;
2. 咨询以后,有没有进入预约、到店、成交;
3. 哪类内容有效,能不能反过来影响下一轮选题。

交付停在"多做几篇内容",没进入后面的获客和成交工作流。**当时的付费只证明了"客户愿意为第一次省事付钱"**,没证明客户需要持续购买、产品会随使用积累上下文、交付会进入成交形成可反复验证的闭环。

> 对应到现有 skill:这是阶段一「成功标准定义」缺失 + 阶段四 land-and-expand 没接到业务闭环的典型后果。

### 价值分配:先让客户得到 100,再讨论你拿 5

> 你想变现,就先让别人赚钱。别人赚大钱,你赚小钱,这件事大家都愿意做。

这不是讨论某一种收费方式,而是:**想收客户的钱,先让客户得到一笔看得见、算得清的价值。** 这笔价值通常落在三处:
- **降本**:原来要花的钱,现在少花了;
- **增效**:同样的人和时间,做得更快、更多或更稳;
- **增收**:原来容易流失的咨询、成交或复购,现在增加了。

说不清客户到底少花了什么钱、省下什么时间、增加什么收入,客户就很难判断为什么要付钱。反过来,产品能让客户得到 100 的可核验价值,你再讨论拿 5,双方更容易长期合作。(100 和 5 只是分配逻辑,不是固定金额/比例。)收费方式(试用费/项目费/订阅/结果分成)放在价值之后讨论;按结果分成只在结果、基线、归因、数据口径都说得清时才适合。

## 6. 让现场反过来塑造产品:下一次别从零开始

### 一次成功,只能证明这一次走通了

一次付费不能直接推出:换一家门店同样有效 / 不靠你本人盯着也能稳定交付 / 客户会持续使用续费。从 0→1 以后,最重要的动作不是马上扩功能,而是把下一次交付和这一次放在一起比较:哪些材料每次都要收?哪些判断每次都要做?哪种结果真被拿去用了?哪里总要人工解释?哪部分只是这家门店自己的情况?

> FDE 和普通外包真正拉开距离的地方,不是做得更多,而是**每做完一次,产品里有没有多留下一点下一次还能用的能力**。呼应阶段一「乙方自检:有没有内核平台」——本节给出把内核长出来的操作方法。

### 每次交付后,只把东西分成三堆

朴素门槛:**同一种做法至少在两次真实交付里出现,才列为"可复用候选"。** 两次不是普遍规律,只是提醒:只出现过一次的聪明做法,先别急着写进核心产品。

| 堆 | 内容 | 处置 |
|---|---|---|
| **① 重复基础** | 多家客户都重复的部分:常出现的输入字段、AI 反复参考的业务知识、验收角色真正会看的结果结构、结果交给谁何时交、下次要回收什么反馈 | 继续验证,有机会变成下一家可直接使用的基础能力 |
| **② 客户特例** | 只属于这家客户的部分:自有项目名/价格/规则、老板偏好的表达、特殊岗位/流程/活动、只有这次才出现的例外 | 可配置、补充或单独处理,**别因一个客户提过就塞进所有人的产品** |
| **③ 人工责任** | 必须由人决定的部分:授权/隐私/脱敏是否合格、有争议的业务判断、风险表达能否使用、特殊顾客和异常情况是否停止自动处理 | **不能为了"看起来更自动化"就删掉人工确认** |

> 该重复的留下,该个性化的分开,该由人负责的绝不假装自动。第③堆和阶段三「三条禁区线」是同一条原则:人工责任不能用自动化覆盖。

> 🔗 **正交澄清(三堆法是 0→1 筛,别和下游的放大混):** 三堆分类法回答"沉淀什么"——把现场交付分成可复用 / 需改造 / 一次性,筛出值得放大的部分,是 **0→1 的筛选**。筛完之后怎么放大,是另外两件事、两个阶段:**① 跨客户复制放大**(1→10→100)见 `scaling-playbook.md`「三级杠杆」(知识复制 → 组件复制 → 产品复制);**② 单客户内扩散**(把已验证的价值长到更多部门 / 场景)见 `renewal-and-expansion-playbook.md`「存量深耕三方向」(横向 / 纵向 / 纵深)。**先用三堆筛(决定哪些值得沉淀),再决定走复制还是走深耕**——跳过三堆直接谈杠杆 / 深耕,等于把一次性的东西也当资产,背上维护债务。

### 产品化三道门:0→1、1→10、10→100

不要求客户数量刚好等于 1/10/100,它们是产品要依次跨过的三道门。**顺序一倒,代价很高。**

| 门 | 证明什么 | 动作 |
|---|---|---|
| **0→1** | 有人真的需要 | 拿真实材料做出可核对结果,进入下一步工作;看客户是否愿意继续提供材料、使用或付费 |
| **1→10** | 价值能够重复 | 把多次真实交付放一起,找出哪些输入/判断/结果/交接反复出现;看清哪些仍只能靠人、哪些只是客户特例 |
| **10→100** | 放大稳定部分 | 一套做法已在不同客户和不同使用者身上反复成立,交付成本/异常/责任边界也看清,再把稳定部分做得更自动、更易规模化 |

> 只做过一次就搭完整平台,容易把偶然经验做成昂贵功能(对应阶段三 NO-GO:demo 直接推生产);同一件事已反复做很多次还全靠人记,又会把团队拖进无休止手工交付。

### 载体选择阶梯:重复结构越稳定,载体才越重

找到重复结构后,必须回答:**到底把它沉淀成什么,才能让 AI 下一次稳定地交付同一种价值?** 按重复结构的成熟程度一层层往下选——**这不是一条必须全部走完的升级路线**:

| 层 | 载体 | 适用 |
|---|---|---|
| 1 | **SOP(标准操作流程)** | 人的步骤/交接/检查顺序已反复出现,但仍需人照着做 |
| 2 | **模板** | 输入字段和结果结构已稳定,减少每次重新整理 |
| 3 | **Prompt** | AI 每次都要按同一套业务知识、判断顺序和输出要求处理 |
| 4 | **Skill / 工作流** | 同一任务需连续调用多份材料、多个工具或多个判断步骤 |
| 5 | **Agent(任务型 AI 系统)** | 一个明确角色需在边界内持续完成多步任务,并根据反馈推进 |
| 6 | **产品模块 / APP / 小程序** | 已有多人高频使用,权限/数据/异常/交付责任也逐渐稳定 |
| 7 | **软硬件组合** | 最大阻碍不是分析,而是现场材料很难被持续、合规地留下(如录音工牌) |

判断当前该做到哪一层,只问三件事:
1. 这个结构在几次真实交付里重复出现?
2. 现在最费人的地方到底在哪一步?
3. 做得更重以后,能不能明显提高稳定性、降低交付成本或扩大使用?

> 能用 Prompt 稳定解决,就不必为了显得高级做 Agent;一个 Skill 已能反复交付,也不必马上开发完整 APP。这和阶段三「别过早多 agent 化」是同一个克制原则:复杂度优先放路由/流程,不堆载体重量。

> **对客户讲结果,对交付者讲载体**:客户知道为什么要用,团队才知道下一次怎样稳定交付。

> 🔗 **正交澄清(载体阶梯是选型,不是质检):** 本阶梯是**选型工具**——判断一份现场经验该沉淀成什么载体(SOP / 模板 / Prompt / Skill / Agent / 产品模块),选错了要么过重要么不够用。一旦决定沉淀成某一载体(尤其"打法手册"这个载体),它**合不合格是另一套标准**,见 `scaling-playbook.md`「打法手册三属性」(长在流程里 / 按场景组织七件套 / 有负责人版本折旧)。**先用载体阶梯选对载体,再用对应质检标准保证沉淀得好**——选错载体,质检再严也是在一具错的骨架上雕花。

## 7. 六个教练式 Prompt(分工与使用路线)

> 这六个 Prompt 不是一套要从头复制到尾的大咒语,而是六位分工不同的**教练**。卡在哪一步,就调用对应那一个。判断一个 Prompt 有没有用,只看三件事:有没有把你从观点拉回最近事件、有没有暴露证据缺口、有没有给出唯一的下一次验证动作。Prompt 可以帮你整理和比较,但不能替你创造事实——没有访谈、材料、使用和付款记录时,它只能告诉你"还缺证据"。

**使用路线:**
| 卡在 | 用 |
|---|---|
| 还没有具体方向 | Prompt 01 |
| 已有方向,但不知需求真不真 | Prompt 02 |
| 问题很多,第一版越想越大 | Prompt 03 |
| 节点选好了,但不知怎样做深 | Prompt 04 |
| 已经试用,但不知到底证明了什么 | Prompt 05 |
| 同类交付已发生两次以上 | Prompt 06 |

### Prompt 01｜还没有方向时,从真实经历里找问题

**何时用:** 脑子里只有"电商、私域、Agent"这类大方向,说不出最近一次真实问题发生在哪。
**先准备:** 过去 30 天真正参与或旁观过的工作/经营/生活流程,不需要先想产品。
**用完拿到:** 三条具体流程、每条的证据缺口、一个七天内能完成的验证动作。

```
你是一名 FDE 式业务问题访谈教练。
你的任务不是帮我编创业点子,而是从我真正进入过的工作和生活场景里找问题。

【访谈规则】
1. 先进入访谈状态,不要直接输出答案。
2. 一次只问一个问题,问完停下来等我回答。
3. 我没有提供的事实,一律写"未知",不要替我补。
4. 证据不足前,不建议产品、功能或解决方案。
5. 每完成一条流程,先回顾"已知事实"和"仍缺证据"。

【第一问】
过去 30 天,你反复参与或旁观过哪三条业务流程?
请让我逐条说,不要一次发问卷。

【每条流程必须追问】
- 从什么具体事件开始?
- 谁在其中判断、交接和采取动作?
- 最近一次具体发生了什么?
- 现在怎样处理?为什么仍然不够?
- 问题多久发生一次?不解决会损失什么?
- 对方已经投入哪些时间、人力、数据、流程或钱?
- 能否拿到一份合规、脱敏、获授权的真实材料?
- 使用者、受益者、决策者和付费者分别是谁?

最近事件、当前做法、具体后果、已有成本、真实材料,
五项缺任何一项,都标记为"暂不过关"。

三条流程问完后,按证据强度输出三个候选卡片:
业务流程｜具体角色｜最近事件｜当前做法｜具体后果｜已有成本｜真实材料｜四种角色｜证据缺口｜七天验证动作。
每个候选只给一个下一步动作,不要声称任何候选已经被验证。
```

### Prompt 02｜已经有方向时,把它磨成真需求卡

**何时用:** 已有一个方向,甚至有人说"想要",但不知是否值得马上做。
**先准备:** 一个具体方向,以及最近一次与它有关的真实事件。
**用完拿到:** 一张真需求卡、仍缺的证据、唯一验证动作;材料不够时明确告诉你"暂不过关"。

```
你是一名挑剔的 FDE 需求教练。
我要验证的方向是:[粘贴方向]。

【工作方式】
1. 先进入访谈状态,不要直接写真需求卡。
2. 一次只问一个问题,问完等待我的回答。
3. 每个结论都标记来自"真实事件"还是"我的猜测"。
4. 信息不足前不建议功能,也不替我把故事补完整。

【依次核对】
1. 这件事属于哪一条完整工作流?
2. 问题发生在其中哪个具体节点?
3. 最近一次是什么时候、谁遇到、发生了什么?
4. 对方现在怎样处理?为什么仍然不够?
5. 问题多久发生一次,不解决会损失什么?
6. 对方已经投入了哪些时间、人力、数据、流程或钱?
7. 我能拿到什么获授权、已脱敏的真实材料?
8. 使用者、受益者、决策者和付费者分别是谁?

最近事件、具体后果、已有成本、真实材料必须同时说清。
缺任何一项,就输出"暂不过关"并继续追问。
不要把"客户说想要"当成需求已经成立。

信息齐全后,只输出:
A 一句话真需求卡
B 已有证据(逐条对应我的原始回答)
C 仍缺证据
D 过关 / 暂不过关及理由
E 下一次唯一验证动作
F 本轮明确不做什么
```

### Prompt 03｜从二三十个现场节点中,选出第一版的一两个

**何时用:** 已确认一个真实现场,但里面问题很多,不知第一版该抓哪个节点。
**先准备:** 一张过关的真需求卡,以及这个现场从开始到结束的真实流程、最近案例和可获得材料。
**用完拿到:** 一张现场节点图、五六个问题节点、一两个首版节点,以及为什么暂不做其他节点的证据。

```
你是一名挑剔的 FDE 现场节点教练。
下面是我的真需求卡和真实流程:[粘贴材料]。

【第一步:先把现场摊开】
沿着真实时间顺序,把现场从开始到结束拆成节点。
完整还原真实节点,不按软件页面拆分。
复杂现场通常能拆出二三十个节点,但不要为了数量凑节点。
每个节点只写:谁、在什么时刻、做什么、用什么材料、遇到什么具体问题。
如果流程不完整,一次只追问一个问题;
不要替我补事实,也不要直接设计产品。

【第二步:筛出五六个左右的问题节点】
每个候选节点都必须对应最近发生过的事实或真实材料。
证据不够就少选,不要为了凑数把猜测放进来。
分别判断:
1. 出现频率:高 / 中 / 低;
2. 后果大小:高 / 中 / 低;
3. 真实材料是否可获得;
4. 做出结果后能否在短时间得到真人反馈。
证据不足就写"暂不入选",不要用想象补齐。

【第三步:只选第一版的一两个节点】
优先只选一个节点。
只有两个节点属于同一条问题链,
能被同一份核心材料和同一轮验证串起来时,才允许一起选。

【第四步:把入选节点做深】
为入选节点写清:
用户: 发生时刻: 真实输入:
AI 只做的一步: 业务判断依据: 可核对结果:
紧邻的下一动作: 反馈信号: 人工确认点: 停止条件:

【最后输出】
A. 完整现场节点图
B. 五六个问题节点及对应证据
C. 第一版入选的一两个节点及入选理由
D. 其他节点本轮不做的理由
E. 一张关键节点开工单
F. 七天内唯一验证动作

最后做红队检查:
- 入选节点是否超过两个?
- 两个节点是否真的属于同一条问题链,并能用同一轮验证串起来?
- 是否有节点缺少真实材料或真人反馈?
- 是否把软件功能误写成了业务节点?
- 范围还能不能再窄一层?
```

### Prompt 04｜让 Codex/工程把选中的节点做深

**何时用:** 已选定第一版的一两个关键节点,准备让工程把这条窄链做出一份客户能核对、能使用的结果。
**先准备:** 一份已授权、已脱敏的输入样本,以及本次处理要依据的业务资料和验收标准。
**用完拿到:** 先得到一份围绕当前节点、带依据的结果样本;真人确认后,再得到最简单的展示载体和复现方法。

```
你是一名重视证据、坚持"做窄做深"的 FDE 式产品工程师。
我要做深的关键节点是:[粘贴开工单]。

【开工门槛】
必须包含:选中的一两个同链节点、真实输入、AI 一步、
处理依据、可核对输出、一个下一动作、反馈信号和停止条件。
缺任何一项就先问,不直接做页面。
如果出现新的、属于另一条问题链的节点,只记录到"以后再做",
本轮不得扩进去。
必须确认材料已获得必要授权并完成脱敏。
不能确认时停止,列出缺失项。

【阶段一:先把当前节点做深,不做界面】
1. 只提取样本里真实存在的内容。
2. 列出本次使用的知识来源和判断标准。
3. 完成约定的 AI 处理;证据不足处写"无法判断"。
4. 输出一份结果样本,每条判断都对应输入或业务依据。
5. 写清这份结果将进入哪一个紧邻动作。
6. 列出哪些现场节点明确不在本轮范围内。
先把阶段一交给我确认。没有真人确认,不进入阶段二。

【阶段二:选择最简单的验证载体】
在文档、表单、幻灯片、单页 HTML 中,
选择成本最低、足以让客户验证价值的一种,并说明理由。
载体只呈现:真实输入摘要 → 处理依据 → 结果样本 → 一个下一动作。
不扩到其他问题链的现场节点。
不声称浏览器会实时调用 AI,不把演示样本写成真实经营结果。
只保留一个希望客户采取的动作:
继续提供材料 / 安排试用 / 修改结果 / 支付试用费。根据当前证据只选一个。

【完成后自检】
1. 陌生人能否在 30 秒内说出:谁用、输入什么、得到什么?
2. 哪一步用了 AI,依据是什么?
3. 结果能否被真人核对?
4. 是否只解决入选的一两个同链节点?
5. 是否只有一个下一动作?
6. 哪些只是演示,哪些已经真实实现?
7. 怎样本地打开或复现?
```

### Prompt 05｜复盘采用、影响与商业证据

**何时用:** 已完成一次现场演示/真实试用/交付,手里有聊天、操作、修改、付款或继续使用的原始记录,但不知这些行为到底能证明什么。
**先准备:** 一份按时间记录、已获必要授权并完成脱敏的真实使用材料。只有总结、回忆或"客户反馈很好"时,先补原始记录。
**用完拿到:** 当前最高证据层级、采用阻碍、已改变的下一步、仍缺证据、下一轮唯一验证动作。

```
你是一名严格的 FDE 采用与影响复盘教练。
下面是本轮演示、试用或交付记录:[粘贴原始记录]。

【材料门槛】
先确认记录已获得必要授权,
并移除姓名、门店、电话、头像和聊天身份等信息。
不能确认时停止处理,列出缺失项。
每条记录至少要包含:
时间｜角色｜原始行为或原话｜当时使用了什么结果｜
结果进入了哪一步工作｜之后发生了什么。
缺少的字段写"记录不足",不要推断。
如果只有转述、总结或情绪评价,标记为"弱证据"。

【事实规则】
- 不根据语气猜测购买意愿。
- 不把"挺好、很厉害"写成采用。
- 不把提供材料写成持续使用。
- 不把现场演示写成已经持续使用。
- 不把一次使用写成复用。
- 不把预约意向写成已经付费。
- 不把一次付费写成续费或经营改善。

【按时间线提取】
1. 客户原来要解决的具体问题、想拿到的结果是什么?
2. 用户提供了什么真实材料?
3. 谁在什么时刻查看或使用了结果?
4. 结果进入了哪一步原工作流?
5. 用户采用了什么、修改了什么、忽略了什么?
6. 哪里需要人工解释或额外操作?
7. 是否第二次使用、付费、续费、扩展或转介绍?
8. 是否出现可以核验的业务结果?

每条证据都输出:
时间: 角色: 原始行为或原话:
进入的工作节点: 支持的最窄结论:
状态:已发生 / 尚未发生 / 记录不足

【证据分层】
称赞 → 继续聊 → 给真实材料 → 真实使用 →
首次付费 → 复购扩展 → 经营改善
只报告当前已经到达的最高一层,不能用低层证据替代高层结论。

【采用诊断】
分别检查:看得懂｜信得过｜不麻烦｜有下一步。
每一项写:现有证据、具体阻碍、最小修改。

【最后输出】
A. 行为时间线
B. 当前最高证据层级及对应证据
C. 四项采用诊断
D. 结果到底改变了哪一步工作
E. 仍缺证据
F. 继续 / 修改 / 停止建议
G. 下一轮唯一验证动作

最后做红队检查:
- 有没有把称赞写成采用?
- 有没有把预约写成付款?
- 有没有把一次付费写成持续产品?
- 有没有在没有基线和归因时声称经营改善?
发现任何一项,就把结论退回证据真正支持的层级。
```

### Prompt 06｜找出下一次不必从零开始的部分

**何时用:** 同一类问题已发生过至少两次真实交付/真实使用,想比较它们,找出哪些部分可留给下一家客户继续用。
**先准备:** 至少两次获授权、脱敏的真实记录(最好含原始材料、处理依据、结果、下一动作、用户实际行为、修改和失败)。
**用完拿到:** 三份清单(可重复的基础部分 / 客户特例 / 必须人工判断的地方)+ 一个最轻的沉淀方式 + 下一次验证动作。
> 这段是给做产品的人用的,不是拿去给老板讲概念。面对老板,仍只讲清问题、结果和下一步。

```
你是一名谨慎的 FDE 产品化复盘教练。
我会给你至少两次真实交付或真实使用记录:[在这里粘贴记录]
你的任务不是替我想更多功能,
而是找出:下一次遇到同类客户时,哪些部分不必再从零开始。

【第一步:先检查记录能不能比较】
每次记录至少要包含:
1. 谁遇到了什么具体问题;
2. 提供了什么真实材料;
3. AI 按什么业务知识或标准处理;
4. 交付了什么结果;
5. 结果进入了什么下一步;
6. 用户实际采用、修改或忽略了什么;
7. 出现了什么失败、异常或人工介入。
如果只有页面截图、产品设想、内部测试或一句"挺好用",
请标记"还不是可比较的真实交付",列出缺失记录,停止做产品化结论。
先确认材料已获必要授权并完成脱敏。不能确认时停止处理,只列出缺失项。

【第二步:逐次还原事实】
为每次交付分别输出一张简短交付卡:
具体客户与场景 / 真实输入 / AI 处理依据 / 可核对的结果 /
进入的下一步工作 / 用户实际行为 / 人工修改 / 失败与异常。
缺少的内容写"记录不足",不要猜。

【第三步:只分三类】
A. 重复基础:列出在两次以上交付中都出现的输入、判断、结果、交接和反馈。
   每一项都写明出现次数和对应记录。
B. 客户特例:列出只属于某一家客户、某一次活动或某个特殊流程的内容。
   不要因为出现过一次,就建议放进所有客户的核心产品。
C. 人工责任:列出涉及授权、隐私、风险、争议判断和异常处理的人工确认点。
   不能为了自动化而删除。
注意:出现两次,只能叫"复用候选",不能直接叫成熟标准。

【第四步:选择最轻的留下方式】
从下面选择当前最简单、下一次就能验证的一种:
操作卡或检查清单 / 表单或结果模板 / 可重复使用的提示词 / 固定工作流 / 产品功能。
说明为什么选它,以及为什么现在还不需要做得更重。

【最后输出】
1. 下一家客户可以直接复用什么
2. 仍然需要单独了解什么
3. 哪些地方必须由人决定
4. 当前最轻的沉淀物
5. 下一次真实交付只验证哪一件事
6. 哪些内容暂时不应进入核心产品

没有真实证据的地方写"尚未验证",不要补数字。
最后做一次红队检查:
- 有没有把一次成功写成普遍规律?
- 有没有把客户特例写进核心产品?
- 有没有为了自动化删掉人工责任?
- 有没有一上来就建议做完整系统?
发现任何一项,就把结论退回证据真正支持的层级。
```

## 8. 七天行动卡:别再想一个月

> 方法都懂了却还在继续整理、继续想——七天给自己一个足够短的期限,逼这条链真正动起来。七天不是做完一套 APP,也不保证一定能收钱;它只跑一条最小但真实的链:**一个真实问题 → 一份授权材料 → 一个可核对结果 → 一个真实用户使用 → 一个更强的行为证据 → 一个继续/调整/停止决定**。

### 七天三段

- **第 1-3 天(先证明问题和材料是真的):** 选中一个窄节点,回到最近一次真实事件,找到正在承担成本的人,拿到一份获授权、脱敏的真实材料。
- **第 4-5 天(让 AI 结果进入一次真实工作):** 先用一份样本做出可核对的结果,再交给一个真实用户,看他有没有拿去做下一步。
- **第 6-7 天(用客户行为决定下一轮):** 提出一个真实请求,看客户愿不愿继续投入材料、时间、组织成本或金钱,然后决定继续、调整还是停止。

### 开始前的四个条件

- 熟悉一条具体业务,或能跟着熟悉业务的人进入现场;
- 七天内能接触至少一位真实当事人;
- 能合规取得一份授权、脱敏的真实材料;
- 愿意接受客户行为可能推翻自己的想法。

> 如果只有 AI 能力、没有行业/客户/材料入口,第一项任务不是做页面,而是先进入一条真实业务。

### 七天行动卡(直接复制使用)

```
【本周只验证的一件事】
具体场景:
真实角色:
真实输入:
AI 处理依据:
可核对结果:

本周明确不做:

【第 1 天｜定范围】
```

### 跑完手里至少要有五样东西

一份最近事件记录、一份授权材料、一份可核对结果、一次真实使用记录、一个继续/调整/停止的决定。它们不一定漂亮,但能防止用后面的产物替代前面的证据:**没有真实材料,页面再漂亮也只是演示;没有使用记录,功能再完整也不能证明采用;没有持续行为,一次付费也不能证明产品已经成立。**

> 各天的动作要点:
> - **Day 1:** 忍住做产品;把任务压成一句话——"在【场景】里,【角色】提供【输入】,AI 按【依据】生成【可核对结果】,帮他完成【紧邻下一动作】"。留下:一句小闭环定义 + 本周明确不做的内容 + 3-10 位可联系的人。
> - **Day 2:** 找三位真实的人聊最近一次(不问"如果有 AI 工具你会不会用")。三个人都说"听起来挺好"不算需求成立;至少一人能说出最近具体事件并愿继续验证。
> - **Day 3:** 向其中一位提出第一个真实请求——给一份材料;同时索取判断依据(项目资料/服务标准/样本/禁用表达/风险边界)和核对人。
> - **Day 4:** 先处理一份样本(不批量跑);结果满足四条件(能回原始材料/能看见业务知识/真人能判对错/看完知道下一步);业务方逐条标记准确/错误/缺证据/需人工。
> - **Day 5:** 把结果交给一个真实使用者,坐在旁边观察(看懂没?信吗?改了哪?跳过哪?有没有真进入跟进/训练/决策?)。只允许一次最小修改,优先删步骤/缩结果/补依据/说清下一动作,不要因用户卡住就加功能。
> - **Day 6:** 别再问"觉得怎么样",根据证据提出一个强度匹配的请求(再给材料/让第二位用户试/连续几天使用/小额内测费/正式合作)。对方只看过一次结果,先别谈长期合同。
> - **Day 7:** 只做三个决定——继续(下一轮只扩大一个变量)/ 调整(回到最早断掉的那一步,缩小范围或改输出)/ 停止(找不到最近事件、始终拿不到合规材料、结果无人使用、客户不愿承担任何新成本——页面做了很多不是继续投入的理由)。

## 9. 红队检查清单

每次给出结论前,逐条自查。命中任何一条,把结论退回证据真正支持的层级。

| # | 红队问题 | 命中后的纠正 |
|---|---|---|
| 1 | 有没有把"称赞/挺厉害"写成采用? | 退回到"看到了结果",要采用行为证据 |
| 2 | 有没有把"预约意向"写成"已付费"? | 两个数字分开:已发生付款 ≠ 预约意向 |
| 3 | 有没有把"一次付费"写成"持续产品/续费"? | 一次付费只证明当下有人愿意买 |
| 4 | 有没有在没基线和归因时声称经营改善? | 老实停在采用和行为层 |
| 5 | 有没有把"一次成功"写成"普遍规律"? | 至少两次真实交付才算复用候选 |
| 6 | 有没有把"客户特例"写进核心产品? | 特例配置化,不进所有人产品 |
| 7 | 有没有为了自动化删掉人工责任? | 授权/隐私/风险/争议判断必须留人 |
| 8 | 有没有一上来就建议做完整系统/多 agent? | 选最轻能验证的载体,Prompt 能解决别上 Agent |
| 9 | 第一版是否超过两个节点?或两个节点不属于同一条问题链? | 继续做窄,直到一份核心材料穿过一条最短价值链 |
| 10 | 有没有把"软件功能"误写成"业务节点"? | 回到现场,按真实时间顺序拆节点,不按软件页面 |
| 11 | 三个乘项(真问题/可用结果/进入工作/持续使用)有没有接近零的? | 哪项塌了回哪一步补,别靠加功能盖过去 |
| 12 | 范围还能不能再窄一层? | 默认再窄一层 |

> 贯穿全程的三句自检(来自案例):
> 1. 这事,真值得做吗?(真需求)
> 2. 第一版,到底小到哪一步才算完?(小闭环)
> 3. 客户说好以后,愿不愿意掏钱、花时间、给材料?(真付费)
