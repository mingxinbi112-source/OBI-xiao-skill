核心信念(贯穿全篇):**FDE(Forward Deployed Engineering)不是"会调模型 API 的全栈工程师",而是对"高价值 AI 工作流"负最终工程责任的人。产物不是 demo,是上线后稳定的系统、可审计的流程、可扩展的运维、持续可提升的指标。** 真正的 AI/ML 生产系统同时承受**代码、数据、模型**三条变化轴,FDE 的价值就是把这三轴收束成一个能活下去的系统。

## 🎯 一、控制面 vs 执行面:先把系统拆两半

**实操翻译:** 正确的生产架构观不是"所有需求都做成 agent",而是先把系统拆成两层:
- **控制面(control plane):** 计划、路由、策略、评估、版本管理、人工介入门控。它决定"这次请求该走哪条流程、用哪个模型版本、要不要拦下来给人审"。
- **执行面(data/execution plane):** 检索、特征读取、模型推理、工具调用、事务落地。它老老实实干活,动作都可观测、可审计。

**为什么必须拆:** agent 在生产里不是"对话循环",而是**一个需要状态机、审计轨迹、审批门控的应用运行时**(LangGraph 把 agent 建模为 graph,强调长时运行/持久化/故障恢复/human-in-the-loop;OpenAI Agents SDK 把 state、guardrails、human review、tracing 作为一等公民)。把控制逻辑(该不该做、走哪条路)和执行逻辑(具体怎么做)混在一个 agent 里,是后期不可治理的根源——你改不了路由策略、加不了审批门、出事定位不到是哪一层。

**✅ 合格检查点:**
- 能在一张图上画出控制面(路由/策略/评估/审批)和执行面(检索/推理/工具/事务)的边界,控制面动作可独立配置、独立发版。
- 路由策略(哪个 intent 走哪个 routine)是**可独立修改、可灰度**的,不需要改 agent 本体。
- 所有执行面动作都挂在控制面的观测/审批钩子上,不存在"agent 绕过控制面直接落地事务"的旁路。

**💀 致命场景:** 把路由、推理、工具调用、审批全塞进一个"超级 agent",结果改一个 routing 规则要重发整个 agent、加一道审批门要改 agent 代码、出事时整条链路无法分段定位——系统从"可治理"退化为"一个黑盒"。

> 和权限禁区的呼应:控制面/执行面分离是"划禁区"在架构层的落地——禁区(审批门、kill switch、置信度门)必须挂在控制面上,才拦得住执行面。详见 `permissions-and-oversight.md`。

## 二、代码/数据/模型三轴:MLOps 骨架的"为什么"

**实操翻译:** 真正的 AI/ML 生产系统同时承受三条变化轴,必须作为**可重复发布的工件**一起管理:
- **代码(code):** 模型代码、特征工程、prompt 模板、agent 逻辑——Git 版本化。
- **数据(data):** 训练数据、评估集、特征——版本化 + 可追溯(DVC / dbt contracts)。
- **模型(model):** 模型权重、配置、指标——注册表 + 版本号(MLflow Model Registry)。

**为什么这是 MLOps 骨架存在的根本理由(CD4ML):** Martin Fowler 的 CD4ML 明确,机器学习应用必须把 code/data/models 作为可重复发布的工件一起管理;Google《Hidden Technical Debt in Machine Learning Systems》更点破——**ML 系统的大头难度不在模型本身,而在耦合、依赖、反馈回路和不可见技术债。** 这就是为什么 `mlops-playbook.md` 里的六大骨架(实验追踪、模型注册/回滚、数据版本、流水线、部署、监控)不是"锦上添花",而是"不搭就死"。

**对 FDE 评估的含义:** 阶段三判断"能不能上生产",本质是判断"这三轴有没有被一起管起来"。一个"模型代码在 Git、训练数据在某人本地、模型文件丢在某个服务器路径"的项目,三轴是断的——它复现不了、回滚不了、追责不了,离生产差一整个 MLOps 体系。

**✅ 合格检查点:** 给定线上任意一次预测,能回答"它是哪个 code 版本 + 哪个 data 版本 + 哪个 model 版本产出的"——三轴版本三元组对得上,才算可复现。

**💀 致命场景:** 改了特征代码没重新训练、或线上推理特征和训练时不一致 → 模型 silently wrong(静默错误),查三天查不出。这就是 `mlops-playbook.md` 反复强调"特征代码必须和模型代码同仓库同版本"的根因。

> 六大骨架的具体合格检查点/致命场景/起步操作见 `mlops-playbook.md`;本节只回答"为什么必须有"。

## 三、单 agent vs 多 agent:别过早多 agent 化

**实操翻译:** 这是 FDE 在 agent 时代最容易踩的架构坑——一上来就搭层层 agent hierarchy,觉得"多 agent = 更先进"。错。**复杂度应该优先放在路由与流程建模,不要优先放在 agent 数量上。**

**Klarna 的实战经验(最常被引用也最常被误读的案例):** Klarna 的客服 AI 上线第一个月完成 230 万次对话、承担三分之二客服量、约等于 700 名全职坐席,靠的**不是**一大堆复杂 agent hierarchy,而是**单 agent + 极强的 routine retrieval / intent routing**——在大量 routines 中把"该走哪条流程"尽量早、尽量准地选出来。

**什么时候才值得上多 agent(满足任一才考虑):**
1. 问题**天然可分解**成几个独立子任务(如"先查库存、再算运费、再生成报价"可并行)。
2. 单个 agent 的**工具上下文过宽**(塞了几十个工具,模型选不准)——拆成几个窄 agent 各管一域。
3. **多并行子任务明显增益**(一个一个串行跑太慢)。

**默认起点:** 先用**单 agent + 强检索 + 强路由**把大量 routines 选准;把 agent 工作流当 graph 先画清楚(哪个节点干什么、人工在哪介入),再决定要不要加 agent 数。LangGraph 的定位就是"低层编排框架"——先把图画清楚是第一职责。

**✅ 合格检查点:**
- 架构选型能回答"为什么需要 N 个 agent"——答得出具体收益(可分解 / 上下文过宽 / 并行增益)才上多 agent;答不出就先单 agent。
- 路由层(intent → routine)是独立、可评估、可灰度的,有"路由正确率"指标。
- 多 agent 之间的状态传递、失败回退、审计链路已设计清楚。

**💀 致命场景:** 没有路由设计就堆了 5 层 agent,每层都"理解"一遍用户意图,延迟爆炸、成本翻倍、出事时分不清是哪层 agent 理解偏了——典型的"用 agent 数量掩盖路由设计的懒惰"。

> 和"克制"铁律的呼应:会划禁区的人,在架构上也克制——能单 agent 解决就不上多 agent,能确定性 pipeline 解决就不上 agent(见第五节"混合模式")。

## 四、KPI 四层 + trace 完备性硬标准

### KPI 四层(让"成功标准"从一句话变成可验收体系)

阶段一要求"成功标准必须量化可验收"。但只定一个"准确率"或"调用量"远远不够——**FDE 的 KPI 要分四层**,每层都有可验收指标:

| 层级 | 盯什么 | 典型指标(举例) |
|---|---|---|
| **业务层** | 它到底给业务带来什么 | adoption(采用率)、完成率、人工替代率、平均处理时长、利润/成本改善 |
| **质量层** | AI 输出本身行不行 | eval score、人工复核通过率、任务完成率、路由正确率、重试率、变更回归 |
| **系统层** | 系统跑得稳不稳 | latency/traffic/errors/saturation(Google SRE 四个黄金信号)、队列长度、GPU 利用率、超时率、rollback 频率 |
| **数据层** | 喂给模型的数据还正不正常 | freshness、schema breakage、特征缺失、训练/推理偏差、契约破坏率、质量检查通过率 |

**对评估的含义:** 阶段一签约定"成功标准"时,至少把**业务层 + 质量层**的指标量化锁定(业务层是客户肯不肯付钱的依据,质量层是 AI 行不行得通的依据);系统层和数据层在阶段三 MLOps 设计时补齐。**企业真正关心的是 adoption、工作流影响、单位产出,不是模型 benchmark**——Morgan Stanley 看的是 98% 顾问团队在用、Klarna 看的是 700 坐席工作量,没人在乎它跑的是哪个模型。

> 🔗 **业务价值维度的评估,本文件只列指标分层(四层 KPI);具体怎么"先定义好、再追求好"见 `activation-playbook.md`「评估体系先行」(约翰迪尔案例:与业务专家共建评估集,开工前就定下靶子指标)。** 三者分工:本文件回答"KPI 分几层、trace 要全到什么程度"(工程架构视角);activation 回答"评估集怎么从真实案例长出来、谁当评委"(交付落地视角);上线后这些 KPI 读出什么数、跌破什么线触发什么动作,见 `fde-metrics.md` 四层指标(运营度量视角)。**架构层把 eval 当质量护栏,激活层把 eval 当价值靶子,运营层把 eval 当健康读数——同一个评估体系,三个阶段三种用途。**

### trace 完备性硬标准(生产可维护的及格线)

**一个实用标准:任何一次线上任务失败,你都应该能在一个 trace 里看到——输入、检索、路由、工具调用、模型响应、人工介入、最终结果。** 做不到,系统就还没真正进入"生产可维护"状态。

**为什么是硬标准:** OpenTelemetry 把可观测性收束为 traces/metrics/logs 三件套;OpenAI Agents SDK 把 model calls、tool calls、handoffs、guardrails 都作为可追踪 span;MLflow 把 observability/evaluation/prompt/model 管理放一个平台。FDE 现场排障时,能不能 5 分钟在一个 trace 里定位"是检索召回错了、还是路由走偏了、还是模型幻觉了、还是工具调用失败了",直接决定 MTTR(平均恢复时间)。

**✅ 合格检查点:** 抽查最近 3 次线上失败 case,每次都能在一个 trace 里还原全链路、定位到具体环节。做不到 = 盲飞,上不了生产。

> 系统层/数据层的监控工具栈(Prometheus/Grafana/Evidently/Arize Phoenix 等)见 `mlops-playbook.md` 四层监控;本节回答的是"KPI 怎么分层、trace 要全到什么程度"。

## 五、部署三问:部署在哪 / 状态谁握 / 发布谁控

**实操翻译:** 把 FDE 的部署技术决策压缩成三个问题,逐个回答,选型自然浮现。**不要一上来就追"哪个云功能最多",先回答这三个谁控制权的问题。**

### 第一问:部署在哪里?(runtime + 数据落在什么环境)
- 数据敏感 / 主权要求高 / 有专网 or 政府网络需求 → 倾向自建 K8s 或混合(数据面留专网)。
- 没有强主权约束、要最快交付 → 托管平台(SageMaker AI / Azure ML / Vertex AI 等)更快。
- **关键取舍:你愿不愿意把 runtime、网络、身份边界交给云平台,换更短的交付周期?**

### 第二问:状态握在谁手里?(agent/工作流的持久化状态)
- 长时运行 agent、需要故障恢复和 human-in-the-loop → 状态必须持久化在**你可控的**存储里(LangGraph checkpoint / 数据库),别让状态散在某个托管服务的黑盒内存里。
- 状态在谁手里,谁就握着"任务能不能恢复、能不能审计、能不能迁移"的命门。

### 第三问:发布由谁控制?(CI/CD + GitOps)
- 生产发布必须是**声明式 + 可回滚**的(GitHub Actions + Argo CD 这类 GitOps)——发布动作来自 Git 提交,不是某人在终端敲 kubectl。
- 金丝雀、流量切分、自动回滚是默认配置,不是"以后再补"。

### 现实里的第三种路径:混合式控制面/数据面
**最贴近 B 端现场现实的,常常是混合式:** 模型/agent 编排在托管或统一控制面上跑,但**数据和事务执行留在私有 VPC / on-prem / 政府环境**。Palantir AIP 强调跨多云/on-prem/政府网络部署、OpenAI 政府 FDE 强调 secure compliant deployments——都说明"控制面可上云、数据面不出域"这种组合在现实里是刚需,尤其金融/医疗/政企。

### 轻量选型逻辑(不堆对比表)
- **要可控 / 专网 / 主权 / 跨云可迁移** → 开源自建组合(K8s + KServe 推理 + MLflow 实验/注册 + Feast 特征 + Argo CD GitOps + OTel 观测 + dbt 契约)。可控性最高,但平台工程/SRE/安全/升级/成本治理全得自己扛。
- **要最快从 experiment 走到 prod** → 托管一体化平台(SageMaker AI / Azure ML / Vertex AI)。托管程度高,云绑定也深。
- **数据敏感但不想全自建** → 混合式(控制面托管、数据面留专网)。
- **应用就是一个 API 化的 compound AI service** → BentoML 这类轻打包(vLLM + OpenAI-compatible endpoint + function calling)比上来就铺 KServe 更轻、更适合一线快速扎一个可部署服务。

> 决策原则:**第一阶段别追求"大而全平台统一",先做一条高价值工作流的最短闭环;第二阶段再把被证明有效的控制面抽象成平台。** 这是 FDE 的工作方式,不是传统平台团队先造"大一统中台"再找业务落点。

## 六、发布控制:error budget + rollout gates

**实操翻译:** KPI 定了,还要和**发布控制**挂钩——否则团队为了赶进度会无脑发版,把生产稳定性侵蚀掉。

### error budget(错误预算)
Google SRE 的思想:给关键 SLO 一个"可容忍的不可用额度"。**当 error budget 被持续消耗殆尽(关键 SLO 被持续侵蚀),团队必须暂停高风险变更,优先修复稳定性**——除非 budget 有富余,否则不给上新功能。这给"要不要暂停发版"一个客观依据,而不是靠拍脑袋或吵架。

### rollout gates(发布门禁)+ instant rollback
Uber 的安全部署实践:把"模型/服务健康度"转成**自动化的发布门禁**——新版本先小流量,门禁指标(错误率、延迟、业务指标)达标才放行更大流量,不达标自动回滚。**模型上线安全不是发布前最后一次测试,而是从数据和代码工件开始、贯穿整个生命周期的自动化 safeguard。**

**✅ 合格检查点:**
- 有明确的 error budget 机制(SLO + 预算耗尽 = 冻结高风险发版)。
- 发布是门禁化的(小流量 → 指标达标 → 放量),不达标自动回滚,不靠人盯。
- 回滚演练定期跑(凌晨能自动恢复,而不是第二天才发现)。

> 金丝雀/回滚的 MLOps 落地见 `mlops-playbook.md`「部署与金丝雀」;本节回答的是"发版节奏怎么和稳定性挂钩"。

## 七、三个真实案例的经验教训

> 这三个案例来自官方客户故事与公开技术分享,适合提炼架构与治理经验,不应当作独立审计报告。把它们记牢,是为了在客户面前有"真凭实据"的判断力,而不是空谈方法论。

### Morgan Stanley(金融):先有 eval 和 controls,后有大规模 adoption
- OpenAI 官方案例:Morgan Stanley 对**每个 AI use case 都走评估框架**,专家反馈持续进入改进环;AI @ Morgan Stanley Assistant 被超过 **98% 的顾问团队**使用,顾问知识访问覆盖度从 20% 提升到 80%。
- **给 FDE 的结论:** 对金融/医疗/政企,最重要的启发不是"用了哪个大模型",而是 **先有 eval(评估)和 controls(控制),后有大规模 adoption**。信任是 adoption 的前提,而信任来自可评估、可控。

### Klarna(客服):别把系统过度 agent 化
- OpenAI 官方:AI assistant 上线第一个月 **230 万次对话**、承担**三分之二**客服量(约 **700 名全职坐席**)、平均解决时长从 11 分钟降到不到 2 分钟、重复咨询降 25%。
- **给 FDE 的结论:** 见第三节——复杂度优先放路由与流程建模,不要优先放 agent 数量上。**单 agent + 强路由 + 强检索**打赢了一大堆复杂 hierarchy。

### Uber(Michelangelo):成功案例必须平台化
- Uber Michelangelo 覆盖 end-to-end ML lifecycle;2024 年约 400 活跃项目、月 2 万+ 训练任务、5000+ 生产模型、峰值实时预测 1000 万次/秒;2025 年披露峰值超 1500 万次/秒,并引入贯穿生命周期的 health measurement、rollout gates、instant rollback。
- **给 FDE 的结论:** 第一,**现场交付必须最终沉淀为平台能力**(现场信号 → 平台抽象的正反馈);第二,**模型上线安全是贯穿生命周期的自动化 safeguard**,不是发布前最后一次测试。

### 一句话总结这三个案例
**Morgan Stanley 告诉你先把评估和信任建起来;Klarna 告诉你别把系统过度 agent 化;Uber 告诉你成功案例一定要平台化,否则交付规模一大就被技术债吞掉。**

## 八、合规与安全扩展基线

> `permissions-and-oversight.md` 已覆盖 EU AI Act Art 14、OWASP LLM06(过度代理)、IASR 2026(自动化偏见)。本节补充**工程化的安全合规基线**——把这些要求做成工程默认值,而不是"安全同事来问了再补"。

### NIST AI RMF:把 AI 风险管理分成四个函数
- **Govern(治理):** 谁对什么负责、流程、文档。
- **Map(映射):** 摸清系统的风险面(用了哪些模型、数据、工具、权限)。
- **Measure(度量):** 用 eval/测试量化风险(幻觉率、越权率、漂移)。
- **Manage(管理):** 缓解措施落地(审批门、熔断、回滚)。
- **对 FDE 的含义:** 安全合规不能留给上线前的"审查会",必须体现在日常工程工件里——版本、日志、审批、测试、回滚、责任归属,开发时就设计进去。

### 威胁模型:你交付的是复合攻击面系统
- OWASP LLM Top 10(prompt injection、insecure output handling、training data poisoning、model DoS、supply chain、sensitive info disclosure、excessive agency 等)+ MITRE ATLAS(AI 系统对抗战术)。
- 你交付的不再是普通 web app,而是**可能被用户输入、外部文档、插件/工具、模型供应链、长任务代理共同攻击的复合系统**。

### 六道缓解层(生产级 FDE 系统的默认配置)
1. **权限最小化**(见 `permissions-and-oversight.md` 第三条线:default deny + scoped)。
2. **审批与人工复核**(见第二条线:guardrails + human review + 防 automation bias)。
3. **harness-level observability:** 长任务 agent 的关键控制点在 **harness/运行包络层**——所有动作都经过它,观测和验证最适合挂在这里(Anthropic agent sabotage/monitoring 研究的结论)。这是为什么 trace 完备性(第四节)是硬标准。
4. **供应链完整性(SLSA):** 提升构建完整性与 provenance,降低制品和构建链路被篡改的风险。
5. **内容与数据防护:** Moderation、PII redaction、输出校验、结构化约束内建。
6. **运行时 kill switch:** 一旦发现异常工具调用、越权读取、错误路由或成本失控,系统必须能**暂停、隔离或回滚**。

### 法规时间轴(全球团队必须排进计划)
- **EU AI Act(Regulation (EU) 2024/1689):** 2024 年 8 月 1 日生效,**大部分条款 2026 年 8 月 2 日开始适用**,按风险类别分阶段落地。
- **对 FDE 的现实含义:** 现在设计日志、审计、文档、模型清单、职责分界的方式,很可能决定两年后的合规成本。越早做成工程默认值,后期改造成本越低。

### 工程默认值的实现理念
真正成熟的 FDE 团队,把安全合规做成 **policy-as-code / contracts-as-code / evals-as-code / deployment-as-code**——而不是"靠经验和人工 review 扛住一切"。合同里就把这些列为不可删项(和监控、agent 权限一样,是"砍预算时最先被简化、出事时唯一能救命"的东西)。

## 附录:FDE 团队七项组合能力

> 这是"一个团队的组合能力",不是要求单个人全包。评估一个 B 端 AI 项目能不能成时,也可以用这张清单反查"客户/我方团队缺哪块能力"——缺的那块,就是项目风险点。

1. **业务建模:** 能把模糊流程转成可操作的 system boundary 和 KPI。
2. **Agent 与工作流编排:** 会区分单 agent、图编排、多 agent、确定性 pipeline(见第三、五节)。
3. **数据与契约治理:** 会用 contracts、quality checks、freshness、lineage 控制上游变化(见第二节、`mlops-playbook.md`)。
4. **模型生命周期与评估:** 会做 registry、dataset lineage、trace-based eval、回归比较(见 `mlops-playbook.md`)。
5. **平台与发布:** 懂 K8s、CI/CD、GitOps、金丝雀、回滚(见第五、六节)。
6. **可观测与 SRE:** 能围绕 traces/metrics/logs/SLO 设计仪表盘和告警(见第四节、`mlops-playbook.md`)。
7. **安全与合规:** 能把 prompt injection、权限、供应链、审计做成默认控制(见 `permissions-and-oversight.md` + 本节)。

---

> **一句话收尾:FDE 是 AI 组织把模型能力变成长期业务产出的"最后一公里"系统工程。在 2026 年,这个岗位的上限已经不是"做个聊天机器人",而是重写工作流、重构数据路径、嵌入控制面、量化 ROI,并把现场打法平台化。**
