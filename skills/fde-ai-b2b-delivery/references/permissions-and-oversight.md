# AI 权限与人工监督 Playbook(划禁区,项目负责人视角)

本文件是 `SKILL.md` 阶段三「人机边界 + Agent 权限」的**实操展开**。它回答的不是"要不要给 AI 限权",而是 **"你作为项目负责人,哪些决策权 AI 不能拿、审核怎么设计才不形同虚设、agent 的权限边界具体划到哪、不划的致命后果、从哪起步"**。

2. 第一条线:不可逆决策,AI 不能有最终决定权

8. 合规与标准引用

## 🎯 核心信念:克制 > 激进

> **真正稀缺、也最值钱的本事,不是知道 AI 能干什么,是知道哪些事它碰都不该碰。会让 AI 狂奔的人越来越多,会在正确的地方一把摁住它的人才会越来越值钱。**

三条禁区线指向同一个认知:

- **AI 天生有概率出错,而且错的时候特别自信、特别像那么回事。** 一个会一本正经胡说八道的东西,可以干很多活,但不能把"错一次就完蛋"的事交给它。
- **划禁区表面是给 AI 设限,本质是保护这个系统能长久活下去。** 那些"让 AI 干更多"的项目,绝大多数死在它最激进的地方——在不该用的地方用了 AI,在该有人兜底的地方让 AI 拍了板,在该收权限的地方给了 agent 太大的自由,然后某次自信地犯错,整个项目的信任就崩了。在严肃行业里,一次本可避免的严重错误,足够让一个 AI 系统被彻底弃用。
- **更紧的边界不是自主的敌人,恰恰是自主能成立的前提。** 权限收得越干净越精确,你才越敢放手让 agent 在安全范围里自动跑;边界模糊的 agent 你根本不敢给真正自主,因为你不知道它下一步捅到哪。

这跟"谁让 AI 干得更多谁赢"的行业氛围是反的。FDE 的专业度,很大一部分体现在"克制"上。

## 第一条线:不可逆决策,AI 不能有最终决定权

**实操翻译:** 凡是"错了就无法挽回、或代价你扛不起"的决策,那一锤子必须人落。AI 可以把材料和依据备齐、把候选方案排好、甚至标出推荐项,但**落锤的执行权,物理上不在 AI 手里**。

**怎么判断一条决策是不是禁区——一个标准:**
> 这条决策错了,**能不能挽回?代价你扛得起吗?**

只要答案是"不能 / 扛不起",它就是 AI 禁区(C 类),无论模型在这件事上"看起来有多准"。

**📋 决策权分类清单(照着勾,把场景里的操作填进对应类):**

| 必须人落锤(C 类,AI 禁区) | AI 备料 + 人审核(B 类) | AI 全自动(A 类) |
|---|---|---|
| 放款 / 转账 / 退款审批 | 诊断建议 / 用药建议 | 归档 / 打标签 / 分诊初筛 |
| 手术方案 / 用药最终决定 | 审批 / 定价 / 质检判定 | 抄录 / 对账 / 查档检索 |
| 签约 / 合同条款采纳 | 裁员名单建议 / 晋升建议 | 通知 / 报表生成 |
| 处罚 / 封号 / 拒赔决定 | 风险评级 / 合规初判 | 路由 / 排序 |
| 产线停机 / 解除安全联锁 | 异常预警 / 工艺参数建议 | 数据清洗 / 格式转换 |

> 关键:**B 类是 B 端 AI 的核心价值区,要把它做大做扎实;但"价值大"不等于"能给 AI 拍板权"。** 价值越大的决策,通常代价也越大,越要人落锤。

**✅ 合格检查点:**
- C 类操作在架构上**没有**指向 AI 的执行接口——AI 输出的永远是"建议",落锤按钮的 handler 不在 agent 的工具列表里。
- 系统能在审计时回答:"这条不可逆操作,最终是谁、基于什么、在几点落锤的",且**落锤者是人类**。

**💀 致命场景:** 把"看起来低频、但一旦错就不可逆"的决策(如解除安全联锁、罕见病用药)当成普通 B 类,默认让 AI 在置信度高时自动执行——它九次对,第十次自信地错一次,就是事故 + 信任归零。

**🚀 起步操作:** 项目立项第一周,拉着业务负责人过一遍"决策权分类清单",把该场景所有操作逐条标注 A/B/C,白纸黑字锁定。**这一步是后面所有权限设计的依据,务必早做。**

## 第二条线:破"自动化偏见"——审核不是摆人,是用设计逼审核真发生

**实操翻译:** "高风险的让 AI 做、后面加个人审一下"听起来完美,但它是**虚假的安全感**。

**什么是自动化偏见(automation bias):** 当一个 AI 持续地、流畅地、看着挺靠谱地给你输出结果,时间一长,那个负责审核的人会**不知不觉越来越信它**,审核慢慢退化成橡皮图章。这不是那个人懒,是人脑的天性——机器十次有九次对,人就默认第十次也对,橡皮图章一盖了事。航空业、医疗诊断里早就反复证明过这个效应(International AI Safety Report 2026),放到 AI 上一模一样。

> **你以为设了道防线,其实它在自动化偏见的侵蚀下慢慢变成了摆设。** 出了事还能拿"我们有 human in the loop"挡一下——可"有没有人在回路里"是一回事,"这人是在真审还是在盖章"是另一回事。

**关键认知:审核有不有效,不取决于你放没放人,取决于你的设计逼不逼着这人真的去审。** 三招,专门跟人性的偷懒对着干:

### 招式一:绝不给"一键全部通过"按钮

它是自动化偏见的温床——你给了,人就会用。改成:把每个结论的**出处都标出来**,逼审核人必须**点开、对到原始材料那一行**,才能通过这一条。让"核对"从可选变成必经,他想盖章也得先 check 一眼。

**✅ 合格检查点:**
- 审核界面**不存在**"全部通过 / 批量通过"按钮,只能逐条通过。
- 每条 AI 结论旁有可点击的**原始材料锚点**(对应文档第几行 / 数据库哪条记录),点开才能看到"通过"按钮。

**💀 致命场景:** 图效率做了"一键通过",上线第一个月审核人还很认真,第三个月开始全量一键通过,某个本该被拦下的错误一路绿灯。

### 招式二:分级审核,防"审核疲劳"

如果每件事都要人审,人很快疲劳,疲劳了就开始无脑通过——这叫**审核疲劳**。按风险分层:

- **低风险(A 类倾向):** AI 自己过,只**通知一声** + 留记录。
- **中风险(常规 B 类):** AI 出建议,人**抽审**或**只看摘要 + 异常**。
- **高风险 / 不可逆(C 类边界):** **强制逐条人工**落锤。

把人的注意力从一大堆琐碎里解放出来,集中砸在真正要命的少数决策上。审核疲劳的根源,往往不是事多,是**把不该占用人的事也塞给了人**。

**✅ 合格检查点:** 有明确的分级规则(哪些自动过、哪些抽审、哪些强制人审),且规则是按"错了的代价"排的,不是按"AI 置信度"排的(两者结合更佳)。

**💀 致命场景:** 所有 B 类一律强制人工逐条审 → 审核人一天看几百条 → 第三天起无脑通过,分级形同虚设。

### 招式三:给 AI 装"心虚"机制(置信度门)

让 AI 对每个判断标**置信度**。高置信度正常走;一旦它自己都不确定、**置信度低于阈值,自动停下、强制转人工**。

本质上是让系统在**最可能出错的地方主动把人拽进来**,而不是等人去大海捞针地抓错。AI 越不自信的地方,恰恰是它最容易一本正经胡说的地方——用它的"心虚"当触发器,比事后人工抽检高效得多。

**✅ 合格检查点:**
- 模型对每个判断输出**校准过的置信度**(不是瞎标的高分)。
- 置信度阈值有**业务含义**(如"低于此线的历史错判率 > X%"),不是拍脑袋定的。
- 低置信度 case **自动进人工队列**,不依赖人主动去捞。

**💀 致命场景:** 模型输出的"置信度"其实没校准(明明该 0.5 的它标 0.95),置信度门形同虚设。→ 配合监控层的"置信度分布"指标一起看(见 mlops-playbook 四层监控)。

> **三招的共性:核心都不是"放个人在那儿",是用设计强迫那个审核真实发生。** 这才是 human in the loop 该有的样子——不是摆个吉祥物挡责任,是让人的判断在真正需要的地方真的、有效地介入。

## 第三条线:破"过度代理"——Agent 权限四打法

**实操翻译:** 以前的 AI 主要是"说"(你问它答,最多说错话);现在的 agent 是"做"——它能调工具、动你的真实系统、发邮件、改数据、执行操作。它从一张嘴,变成了一双手。**一双会犯错的手**。给它配多大的活动范围,就是新的禁区问题。

**什么是过度代理(Excessive Agency, OWASP LLM06):** 行业里最常见的生产事故,根本不是模型不够聪明,而是 **agent 的权限没划清楚,它被允许做了本不该有权做的事**。权限给多了、自主给大了,某次理解偏了、或被一段恶意输入带跑了,就捅了篓子。

### 打法一:默认全禁,逐项授权(default deny)——最核心的一条

别图省事甩给 agent 一把大权限的钥匙、然后指望它变乖。正确方向反过来:**默认它什么都不准碰,然后一项一项地、明确地开权限**。它需要读 A 表,就只开 A 表的读权限,别的一律不给。

> 两个方向最坏情况天差地别:**默认全禁,最坏是它少干了点活;默认全开,最坏是它捅了个你兜不住的篓子。**

**✅ 合格检查点:**
- Agent 的工具/权限清单是**白名单制**(默认 deny,显式 allow),不是黑名单制。
- 每项授权能回答"为什么它需要这个"——需要不了的,不开。
- 权限粒度到**具体资源 + 具体动作**(读 `orders` 表,而不是"数据库访问")。

**💀 致命场景:** 给 agent 一个"管理员 DB 账号"让它"灵活点",结果它某次理解错任务,DELETE 了不该删的表。

### 打法二:身份化——把 agent 当独立"员工"管,别借你的管理员权限

很多人图方便,让 agent 直接用某个管理员账号的权限去干活——这等于把整栋楼的钥匙都给了它。正确做法:

- 给 agent **单独发一个身份**(独立 service account / API key),这个身份有它自己的、被严格限定的权限清单。
- 凭证**设成短期就过期**(short-lived token),用完即失效,不长期常驻。
- 它能碰什么,**清清楚楚记在账上**;出了事能**精确倒查**:哪个 agent、用什么权限、在几点、干了什么。

**✅ 合格检查点:**
- 每个 agent 有独立身份,**不共享**人的管理员账号。
- 凭证有 TTL(如 1 小时),到期自动失效,不存在"永久 key"。
- 所有 agent 的工具调用有**不可篡改的审计日志**(who/what/when)。

**💀 致命场景:** agent 复用了某个离职员工的 admin token,几个月后没人想起来回收,token 泄露后全网裸奔。

### 打法三:读写分离——破"致命三角"

**致命三角 = 一个 agent 同时具备这三件事:**
1. 能读**敏感数据**(客户信息 / 核心业务数据 / 凭证);
2. 能**对外发送**(联网 / 发邮件 / 调外部 API);
3. 在处理**不可信的外部输入**(网页内容 / 用户消息 / 邮件正文)。

三角凑齐是最危险的组合:它能读你的核心数据,又能联网往外发,中间还在处理一段可能藏了恶意指令的外部内容——那它完全可能被一段网页里埋的指令骗着,**把你的数据打包发给攻击者**(prompt injection 数据外泄)。

**破解:拆开。** 让读敏感数据的 agent **没有对外发送权限**;让对外通信的 agent **碰不到敏感数据**。一个 agent 同时只能占三角里的**一个角**,链条就断了。

**✅ 合格检查点:**
- 画出每个 agent 的"读敏感数据 / 对外发送 / 处理外部输入"三角图,**没有任何一个 agent 同时占两角以上**。
- 敏感数据访问和对外通信之间,有**强制的隔离边界**(不同 agent / 不同网络策略 / 不同权限集)。

**💀 致命场景:** 一个"智能客服 agent"既能查订单(敏感数据)、又能发邮件(对外)、还在读用户消息(外部输入)——用户消息里藏了 prompt injection,agent 把客户订单明细群发给了攻击者。

### 打法四:危险操作设审批门 + 分级 + 预算/次数熔断

跟审核一个道理,给 agent 的操作也分级:

- **不可逆、高代价操作**(删数据 / 转账 / 对外发布 / 改权限):**必须停下来等人批**。
- **低风险操作:** 自己跑,**留完整记录**。

再加一道保险——给 agent 设**硬性的预算和次数上限**:单次任务最多花多少钱、某个贵的工具最多调几次,一旦**触顶自动熔断**。因为 agent 是在循环里跑的,一个 bug 可能让它几分钟烧掉你一大笔钱(疯狂调付费 API / 死循环),这种熔断是最后一道闸。

**✅ 合格检查点:**
- 危险操作清单已定义,且这些操作在 agent 侧**只能生成"待审批"工单**,不能直接执行。
- 有**全局预算上限**(token 成本 / 调用次数 / 执行时长)三道硬熔断,触顶即停 + 告警,不靠 agent 自觉。
- 熔断是**系统级**的(agent 改不了自己的熔断阈值)。

**💀 致命场景:** agent 陷入死循环,一晚上调了 20 万次付费 API,账单爆炸;或一个 prompt 被 injection 引导着不停往外发数据,直到被人发现。

> **四打法连起来的原则:对 agent 来说,更紧的边界不是自主的敌人,恰恰是自主能成立的前提。** 权限收得越干净、越精确,你才越敢放手让它在那个安全的范围里自动跑。

## 第四条线:职业道德底线(人红线)——FDE 自己的操守

> 前三条线是**机器红线**(给 AI/agent 划界:不可逆决策不能让 AI 拍板、审核不能形同虚设、agent 权限默认全禁)。这一条是**人红线**(给 FDE 自己立规矩)。机器红线防的是"AI 闯祸",人红线防的是"人作恶"——而且后者更隐蔽:FDE 手里握着的不是一般的技术,是客户组织最深处的秘密,和越来越大的、代替人做决定的权力。

**为什么单独成节:** 客户把最难看的经营数据、组织权力地图、灰色地带的变通流程都向你敞开,基于一个朴素约定——"你是来帮忙的"。这份信任是 FDE 模式的地基,**毁掉它只需要一次越界**。三条机器红线做得再扎实,挡不住一次人红线的失守。

> 来源:后记「FDE 的职业道德」。四条线一起构成完整边界:机器红线管系统怎么设计,人红线管 FDE 自己怎么做人。

### 第一条:数据的主权属于客户

在客户现场看到的数据,**一个字节都不应该出现在不该出现的地方**——不进 AI 的训练数据(除非合同明确授权)、不进案例素材(除非客户书面同意)、不进你下一份工作的谈资。数据访问的最小化原则不只是技术规范,也是职业操守:能不看的就不看,能脱敏的就脱敏。

> 💀 **反例:** 把 A 客户脱敏后的数据/经营细节,用到 B 客户的演示里"显得更专业"——一旦被发现,你在整个行业小圈子里的信誉就清零。企业市场是记仇的,一次公开化的失守,会被反复咀嚼多年。

### 第二条:诚实报告结果,包括坏消息

按结果收费的模式里,最大的道德风险是**粉饰结果**——把"系统上线了"包装成"价值实现了",把相关性包装成因果。`references/fde-metrics.md` 那套价值度量系统,既可以是最诚实的工具,也可以是最精巧的谎言机器,区别只在人心。FDE 的立身之本是"敢被检验",那么被检验出不好的结果时,也要有同样的心态呈上去。

> 💀 **反例:** NRR 算出来难看就换个口径让它"好看一点";试用阶段只汇报成功 case、把失败 case 藏起来——这正是 `references/scaling-playbook.md`「失败复盘」要反对的"修饰过的失败毫无教学价值"。

### 第三条:不制造依赖,不贩卖恐惧

这个行业存在两种隐蔽的恶:一种是**故意把系统做成黑箱**,让客户永远离不开你;另一种是**夸大"不用人工智能就会死"的恐慌**来促成交易。高德纳预测 2028 年前 70% 的企业将因成本与技能空心化,被迫放弃前置部署主导的方案——这个预测是对全行业的警钟。健康的 FDE 模式应该是"**做完会走**":知识转移给客户,能力沉淀给客户团队。让客户强大,而不是让客户上瘾。

> 💀 **反例:** 故意不做知识转移("教会客户我就没饭吃了"),或用"不上 AI 你的竞争对手就把你干掉"来逼单——这是赚依赖的租金,迟早反噬。

### 第四条:把"被替代的人"当回事

FDE 交付的系统,在很多场景里确实会替代一部分人的工作。`references/activation-playbook.md` 讲了大量"变革管理"的技术(三组人物、受损者的出路),但技术之外是伦理:**不要在被替代者面前庆祝效率,不要在方案里把人写成"成本项"而不给出路,不要对自己"正在改变谁的命运"装糊涂。** 技术的中立是神话,部署者的选择是现实。

> 💀 **反例:** 在裁员背景下的项目启动会上大谈"降本增效 X%",对被替代岗位的人没有过渡安排——这会激起最顽强的地下抵抗,且于人道有亏。

### 第五条:对"客户要求但不该做的事"说不

你会遇到游走在合规边缘的要求:"帮我们把员工的行为监控做得再细一点"、"这些数据合规上有点模糊,但先接了再说"。"法国侍者"的隐喻在这里有最深的含义——**真正的专业,不是满足客户的一切要求,而是敢于引导客户走向对他真正有利、也对世界无害的方向。** 说不的底气,来自你账上有别的客户;所以道德,从来也和商业模式有关。

> 💀 **反例:** 客户要一个明显侵犯员工隐私/踩合规红线的功能,为了合同金额硬接——一旦东窗事发,锅全在供应商头上,客户会说"是你们实现的"。

### 第六条:记住你代表的是"技术"本身

对很多客户而言,你是他们接触人工智能的**第一张人脸**。你的每一次夸大,都在透支整个行业在他们心中的信用;你的每一次兑现,都在为整个行业存款。当人工智能越来越深地进入社会的运转,部署者就是技术与人类日常之间的**最后一道翻译**——翻译失真的代价,由所有人支付。

> 💀 **反例:** 为了拿单,把 demo 效果夸得神乎其神,落地后差距巨大——客户从此对所有 AI 供应商都带防备,这个信任缺口是全行业一起还的债。

### ✅ 人红线自检清单

- [ ] 现场数据访问遵循最小化,未经书面授权不进训练/案例/谈资。
- [ ] 价值报告同时呈现坏消息,NRR/达标率不"美化口径"。
- [ ] 合同里写明知识转移承诺("做完会走"),不把客户做成黑箱。
- [ ] 方案里对被替代岗位有明确过渡安排,不把人当"成本项"。
- [ ] 对合规边缘的"特殊需求"有明确的拒绝路径,不因合同金额硬接。
- [ ] 对外承诺与实际交付一致,不夸大不画饼。

## Agent 上生产前权限审计清单(逐项过)

把这张清单当作阶段三 Go/No-Go 的子检查表。**任何一项不达标,agent 不准上生产(可降级为"仅建议、不执行"模式)。**

| # | 审计项 | 达标标准 | 不过的后果 |
|---|---|---|---|
| 1 | 默认权限策略 | 白名单(default deny),非黑名单 | 默认全开 = 过度代理温床 |
| 2 | 权限粒度 | 到具体资源 + 动作,非"DB 访问"这种粗粒度 | 一权多用,越权难追 |
| 3 | 身份独立 | 独立 service account,不借人/管理员账号 | 出事倒查不到、回收不了 |
| 4 | 凭证生命周期 | 短期 TTL,用完即失效,无永久 key | 凭证泄露后长期裸奔 |
| 5 | 致命三角 | 无 agent 同时占"读敏感/对外发/外部输入"两角以上 | prompt injection → 数据外泄 |
| 6 | 危险操作审批 | 删/转/发/改权限只能生成待批工单 | agent 误操作不可逆事故 |
| 7 | 预算熔断 | 全局成本/次数/时长三道硬熔断,系统级 | 死循环烧钱 / 持续外泄 |
| 8 | 审计日志 | 所有工具调用 who/what/when 不可篡改 | 出事无法定责 |
| 9 | C 类禁区 | 不可逆决策无指向 AI 的执行接口 | AI 自信地拍错一次 = 信任崩塌 |
| 10 | 审核有效性 | B 类已做防自动化偏见设计(禁一键通过/分级/置信度门) | 审核退化为橡皮图章 |

## 客户/法务话术:为什么"划禁区"是为你好

客户(尤其激进的客户)常会问:"为什么不让它全自动?为什么要人工卡一道?这不够先进。" FDE 要能讲清楚**克制才是专业**,而不是显得"我们能力不够只能加人"。

### 对激进客户的"刹车话术"

> "X 总,我理解您希望它越自动越好,但我们坚持在某些环节留人工卡口,不是因为技术做不到,恰恰是因为我们见过太多'全自动'翻车的案例。AI 这东西有个特点:它错的时候比什么时候都自信、都像那么回事。在归档、初筛这种错了能挽回的地方,我们让它全自动;但在放款、签约、停机这种**错一次就不可逆**的地方,我们宁可慢半拍,也要人落最后一锤。这不是落后,这是它能被您一直信任、一直用下去的前提。一个因为某次自信犯错捅了篓子、被全公司禁用的系统,再先进也没有意义。我们给您的是'能扛事'的 AI,不是'看着猛'的 AI。"

### 对法务/合规的"对标话术"

> "我们这套人工监督和权限设计,对标的是 EU AI Act 第 14 条(高风险 AI 系统必须有人工监督)和 OWASP LLM Top 10 的 LLM06(过度代理)。具体来说:不可逆决策保留人工最终决定权;高风险环节的人工审核做了防'自动化偏见'设计(强制逐条核对、分级、置信度门),避免审核形同虚设;agent 权限采用默认拒绝 + 最小授权 + 读写分离 + 预算熔断,防止越权和死循环。这些都是有行业标准背书的做法,不是我们单方面的保守。"

## 合规与标准引用

- **International AI Safety Report 2026** —— automation bias 在航空 / 医疗的实证(支撑第二条线:为什么"加个人审"会退化为橡皮图章)。
- **EU AI Act Article 14** —— 高风险 AI 系统必须设计为可被自然人有效监督(支撑第一/二条线:人工监督要"有效",不是摆设)。
- **OWASP LLM Top 10 — LLM06: Excessive Agency** —— 过度代理风险(支撑第三条线:权限给多了、自主给大了的危害与缓解)。
- 读写分离打破致命三角 / 分级审批防审核疲劳 —— 业界 agent 安全实践(federalnewsnetwork.com《when-ai-agents-act》)。
- 默认拒绝 / 身份化 / scoped 权限 —— agent 权限模型实践(kla.digital《ai-agent-permissions》)。
