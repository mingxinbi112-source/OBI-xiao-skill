# MLOps 实操 Playbook(项目负责人视角)

本文件是 `SKILL.md` 阶段三「MLOps 六大骨架」的**实操展开**。它回答的不是"MLOps 是什么",而是 **"你作为项目负责人,每个组件具体要做什么、做到什么程度算合格、不做的致命后果、从哪起步"**。

## 目录
1. 🎯 核心锚点:P0 三件套先跑通
2. 六大组件实操拆解(合格检查点 / 致命场景 / 起步操作)
3. 四层监控详解
4. P0 / P1 / P2 优先级总表

---

## 🎯 核心锚点:先跑通"三件套"(P0)

> **先把「实验能追踪、模型能回滚、异常能告警」这三件事跑通,其他慢慢补。95% 的项目死在没有这三件基础设施上,而不是模型不够大。**

这三件是生产系统的生命线。资源有限时死守这三件,合同里列为不可删项。这也是阶段三 Go/No-Go 红线的判定依据。

---

## 一、数据与特征版本管理(P1)

**实操翻译:** 你必须能回答"这个模型当时是用哪个版本的数据、哪些特征训出来的"。

**具体做法:**
- 每次训练前,把原始数据快照存到固定位置(如对象存储),用 Git commit hash 或 DVC 版本号标记。
- 特征工程代码必须版本化(Git),特征产出文件也要版本化(DVC)。

**✅ 合格检查点:** 训练脚本启动时,自动把当前使用的数据版本、特征版本打印到日志。

**💀 致命场景:** 改了特征逻辑却没重新训练,或线上推理用的特征代码和训练时不一致 → 模型输出 **silently wrong(静默错误)**,你查三天都查不出原因。

**🚀 起步操作:** 先用 Git + 手动数据快照;复杂了再上 DVC。特征仓库 Feast 可晚点,但 **特征代码必须和模型代码同仓库、同版本**。

## 二、实验追踪(P0)

**实操翻译:** 跑了几十上百次实验,每次的参数、数据、代码、结果都要记下来。

**具体做法:** 每次实验自动记录——超参数、数据版本、代码 commit、硬件环境、训练时长、关键指标(loss/acc/F1 等)。不是手动记 Excel,是在代码里加几行 MLflow 的 log 语句自动上报。

**✅ 合格检查点:** 能随时打开一个页面,按指标排序找到最好的那次实验,点进去看到它所有配置,并能一键复现。

**🚀 起步操作:** `pip install mlflow`,训练脚本里加 `mlflow.log_param()` / `mlflow.log_metric()`,启动 `mlflow ui` 就能看。

## 三、模型注册表 + 一键回滚(P0)

**实操翻译:** 生产环境现在跑的是哪个模型?出问题了能不能一键回滚?

**具体做法:**
- 每次训练完,把模型文件 + 元数据(版本、训练时间、数据版本、指标)注册到中心化的"模型库"。
- 生产部署不是直接指向某个文件路径,而是指向注册表里的某个版本号。

**✅ 合格检查点:**
- 线上出问题,**5 分钟内**能切换到上一个稳定版本。
- 新模型上线前,必须经过 **Staging → Production** 状态流转,不能训练完直接上生产。

**🚀 起步操作:** MLflow 自带 Model Registry,足够用到团队 20 人规模。

## 四、流水线编排(P1)

**实操翻译:** 训练、评估、部署不能每次手动跑,要自动化。

**具体做法:** 把"数据准备 → 特征工程 → 训练 → 评估 → 模型注册 → 部署"串成自动化流水线。触发:定时(每周一凌晨重训)或事件驱动(新数据到达触发)。

**✅ 合格检查点:** 新同事入职拿到代码仓库,**一条命令跑通整条流水线**;不会因为"我本地能跑"而在服务器上挂掉。

**🚀 起步操作:** 先用 GitHub Actions / GitLab CI 写简单 YAML 流水线;复杂了再上 Prefect/ZenML。

## 五、部署与服务(P1)

**实操翻译:** 模型要包装成稳定 API,上线要有安全策略。

**具体做法:**
- 用 FastAPI 把模型包成 REST API,Docker 打包,K8s 或云服务器部署。
- 蓝绿 / 金丝雀发布:新版本先给 5% 流量,监控 30 分钟关键指标没掉,再切 100%。
- 自动回滚:错误率或延迟超阈值,自动切回老版本。

**✅ 合格检查点:** 凌晨 2 点模型挂了,系统能在你醒来前**自动恢复**;而不是第二天才发现昨晚一直报错。

**🚀 起步操作:** Docker + FastAPI 先跑起来;K8s 可先用云托管服务(阿里云 ACK / AWS EKS)降运维成本。

## 六、监控与可观测性(P0,最易被忽略,最致命)

**实操翻译:** 模型上线后,要盯着它有没有"悄悄变坏"。分四层盯(详见下节)。

**✅ 合格检查点:**
- 有一个**值班告警群**,模型指标异常自动发消息,而不是等用户投诉。
- 每月一份**模型健康报告**:数据漂移报告 + 业务指标关联分析。

**🚀 起步操作:** Prometheus + Grafana 先搭;Evidently AI 做简单数据漂移检测,够了。

---

## 四层监控详解

| 层级 | 盯什么 | 怎么发现 / 工具起步 |
|---|---|---|
| **基础设施** | API 延迟、错误率、GPU 利用率、token 成本 | Prometheus + Grafana(传统运维都会) |
| **模型层** | 准确率、置信度、输出分布 | 对比线上预测结果与真实标签(如有反馈) |
| **数据漂移** | 输入数据分布是否漂移 | Evidently AI:自动对比线上 vs 训练数据统计分布,发现"用户突然换了一种问法" |
| **大模型/Agent 专属** | 幻觉率、事实性、prompt 长度/成本 | Arize Phoenix:追踪 LLM 调用链,发现某 prompt 模板突然导致输出质量暴跌 |

## P0 / P1 / P2 优先级总表

| 优先级 | 组件 | 不做的后果 |
|---|---|---|
| **P0** | 实验追踪 + 模型注册表(回滚) | 不知道哪个模型最好,出问题回滚不了 |
| **P0** | 监控告警(基础设施 + 模型层) | 模型挂了不知道,用户骂了才发现 |
| **P1** | 数据版本管理 | 无法复现、无法排查 |
| **P1** | 流水线自动化 | 每次部署靠手动,迟早出错 |
| **P1** | 部署与金丝雀发布 | 无自动回滚,凌晨事故靠人肉 |
| **P2** | 特征仓库 | 中小项目可延后,但特征代码必须版本化 |
| **P2** | 数据漂移 / LLM 专属监控 | 模型慢性死亡,从"好用"变"勉强能用"你都不知道 |

> **按场景动态升权(很重要):**
> - 数据漂移监控在**输入易变**场景(制造业换物料/换模具、风控、推荐)→ **升 P1**。
> - 幻觉监控在 **LLM / Agent** 场景(医疗 RAG、客服、法律)→ **升 P0**。
>
> **一句话:先把实验能追踪、模型能回滚、异常能告警这三件事跑通,其他的可以慢慢补。**

## 附录:制造业 AI 质检专项(领域补强)

> 通用 MLOps 之外,制造业(尤其"监测 + 控制"闭环)有四块领域硬骨头,通用 MLOps 覆盖不到,却是制造业项目死亡的高频原因。FDE 必须单独排查。

### 1. 边缘部署:产线 ms 级延迟,云端不可用

**为什么专项:** 产线节拍快(每秒多件),云端往返延迟 + 断网风险 = 不可用。模型必须跑在产线旁的边缘设备(工控机 / 本地 GPU)。

**✅ 合格检查点:**
- 推理延迟进产线节拍预算(如 ≤ 50ms/件,按实际节拍定)。
- 断网时边缘自治,质检不停。
- 边缘硬件选型 + 采购周期(GPU 常 4-8 周)**算进工期**,别事后才发现没货。

**💀 致命场景:** 上线才发现云端延迟超标,产线被迫降速;或断网质检全停。

### 2. OT 集成与安全联锁:误控 = 停线 / 废品 / 事故

**为什么专项:** "控制工作流"要接 PLC/MES/SCADA,是 IT/OT 融合深水区。工业安全联锁是红线——解除联锁、强控设备的审批常 3-6 个月。

**✅ 合格检查点:**
- 现场跟线一天,摸清 PLC/MES 型号 + 有无接口文档。
- 安全联锁改动审批 ≤ 8 周(>8 周 = 红线,>6 月 = 死局)。
- 控制建议永远"人工一键确认",AI 不擅自停线 / 调机 / 解除联锁。

**💀 致命场景:** AI 误判自动停线或调错参数 → 批量废品甚至安全事故,信任一次性归零。

### 3. 漏检率 vs 准确率:漏检率才是质检灵魂

**为什么专项:** 客户爱盯"准确率",但质检命门是"漏检率"——**漏检一个关键缺陷 > 误报一百个**。一个漏检的严重缺陷流到客户端,就是批量召回 + 品牌事故。

**✅ 合格检查点:**
- 成功标准单独定义**关键缺陷漏检率 ≤ Y%**(不是笼统准确率)。
- 按缺陷严重度分级考核(致命 / 严重 / 轻微分别设漏检红线)。
- 漏检事件可回溯(关联到具体数据版本 + 模型版本)。

**💀 致命场景:** 只追准确率,模型学会"多误报凑准确率",关键缺陷反而漏过去。

### 4. 缺陷长尾 + 换模漂移:制造业数据两个天坑

**为什么专项:**
- **长尾:** 最该防的罕见严重缺陷,样本恰恰最少,模型在这些缺陷上是盲的。
- **换模漂移:** 换模具 / 物料 / 批次 / 光照 → 输入分布变 → 模型可能一夜"变瞎"(数据漂移监控在制造场景必须升 P1 的根因)。

**✅ 合格检查点:**
- 签约前拿到历史缺陷库 + **长尾缺陷采集计划**(持续在生产中收集罕见缺陷)。
- 换模 / 换料自动触发模型健康检查 + 漂移告警。
- 建立换模快速验证机制(换模先跑验证集,确认模型没瞎再放行)。

**💀 致命场景:** 换了一次模具,模型默默失准,废品堆到产线末端才发现;或罕见缺陷从没样本,上线即漏检事故。

---

### 制造业 P0 优先级重排(相对通用 MLOps 的增量)

| 项 | 通用 MLOps 优先级 | 制造业调整 | 理由 |
|---|---|---|---|
| 数据漂移监控 | P2 | **P1** | 换模 / 换料频繁,漂移最致命 |
| 漏检率指标 + 回溯 | — | **P0(验收红线)** | 漏检关键缺陷 = 召回事故 |
| 边缘部署(延迟 + 自治) | P1 | **P0(上产线前置)** | 云端不可用,边缘是物理前提 |
| OT 安全联锁审批周期 | — | **阶段一 No-Go 触发器** | >6 月 = 控制工作流物理不可行 |
| 缺陷长尾采集计划 | — | **阶段一必查** | 无样本 = 模型盲区 = 上线翻车 |

> **制造业一句话:先把「边缘能跑、漏检能控、换模能发现、安全联锁能批」这四件,和通用三件套(实验追踪 + 回滚 + 告警)一起跑通,缺任何一件都别上产线。**
