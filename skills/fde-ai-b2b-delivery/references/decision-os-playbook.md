# 企业决策执行操作系统(Decision OS)方法论 Playbook(项目负责人视角)

本文件是 `SKILL.md` 的**方法论补强层**,回答一个现有四个 reference 都没正面回答的问题:**当客户的诉求是"让 AI 真正进入业务闭环、参与决策、推动处置"而不只是"回答问题/解释指标"时,FDE 怎么评估这件事能不能做、做到哪一层、产物长什么样。**

它和现有 reference 互补、不重复:
- `production-architecture.md` 回答「系统架构怎么拆、KPI 怎么定、部署怎么选」;
- `permissions-and-oversight.md` 回答「禁区怎么划、审核怎么设计、agent 权限怎么收」;
- `mlops-playbook.md` 回答「MLOps 六大组件怎么搭」;
- `scorecard.md` 回答「每阶段怎么打分」;
- **本文件回答「业务语义层怎么统一、交付范围落在闭环的哪一层、AI 结论怎么沉淀成可治理的决策对象、经验怎么沉淀成可复用的行业资产」**——即把"AI 从会聊天走向会做事、敢做事、做对事"这一跃迁,变成 FDE 可评估、可验收的工程判断。

方法论参照:Palantir 的 Foundry / Ontology / AIP(把企业对象、属性、关系、逻辑、动作统一到本体,让大模型在安全边界内读业务对象、调工具、参与运营),以及国内 NEXA Decision OS 等同类"决策执行操作系统"的公开实践。**记这套思想,是为了在客户面前有判断"你的 AI 到底进没进业务责任链"的实据,而不是给某个产品做背书。**

## 🎯 一、为什么 FDE 必须懂"决策闭环"

**企业做 AI 的路径高度趋同,且每一步都会撞墙:**
1. 接知识库 → AI 能回答制度/流程/文档问题(撞墙:回答完,业务还得人工判断、派单、审批、回写);
2. 接数据库/报表 → AI 能解释指标变化(撞墙:解释完,没人敢让它参与处置);
3. 接工具/接口 → AI 能调业务系统(撞墙:能调 ≠ 敢让它直接执行,越权谁负责?失败能回滚吗?审计能复现吗?)。

**共性死因:AI 会回答,不代表企业敢让它参与决策;AI 能调工具,也不代表企业敢让它直接执行。** 因为企业里一个看似简单的问题(如"这张发票为什么建议催收"),背后至少牵涉:目标对象(哪张发票/客户/合同/付款)、业务关系(它们之间怎么关联)、规则依据(逾期多少天触发)、证据来源(数据来自哪张表/哪份合同/哪条政策)、执行动作(提醒/催收/升级审批/暂停授信)、风险控制(谁批/谁执行/能否回滚/如何审计)。这些没被系统化管理,AI 就只能停在"解释器和助手",企业没法把它放进真实业务责任链。

**对 FDE 评估的直接含义(三句话记牢):**
- **"AI 项目做不深"的根因,常常不是模型不够强,而是业务语义、证据、动作这三层没被系统化建出来。** 阶段一体检时,这是比"数据在哪"更深一层的判断。
- **客户说"要 AI 落地",常常自己也没想清楚要落到哪一层。** 用第六节的六层闭环逼他定位,工期可能差一个数量级(看板两周,闭环半年)。
- **交付的真正护城河,不是 prompt 或模型,是「本体 + 证据 + Agent + Action + Trace + 行业 Pack」这套可治理、可复用的资产。** 谁先把它沉淀出来,谁后续交付成本断崖下降。

> 和现有铁律的呼应:"会划禁区"(`permissions-and-oversight.md`)回答的是"AI 不能干什么";本文件回答的是"AI 真正要干的那部分,产物长什么样、怎么治理"。两者是同一枚硬币的两面。

## 🔭 二、交付范围诊断:六层闭环

把企业智能闭环抽象成六步,逐层价值递增、工程量也递增:

| 层 | 名字 | 干什么 | 典型产物 | 没做到这一层的表现 |
|---|---|---|---|---|
| 1 | **Sense 感知** | 采集/汇聚数据事件 | 看板、告警 | "逾期率上升了"——然后呢? |
| 2 | **Understand 理解** | 解释指标/回答问题 | RAG 问答、BI 解释 | "这张发票逾期了"——所以呢? |
| 3 | **Reason 推理** | 沿对象关系+规则推出原因 | Evidence Package、命中规则 | 知道"为什么",但没人推动处置 |
| 4 | **Decide 决策** | 生成可治理的决策对象+推荐动作 | Decision Object、Action Proposal | 有建议,但停在聊天记录里 |
| 5 | **Act 执行** | 审批后落锤、回写状态、留审计 | 已执行 Action、回滚凭证 | 敢建议不敢执行,价值落地不了 |
| 6 | **Learn 复盘** | 用执行结果反哺本体/规则/eval | 更新后的规则、Eval 用例 | 做完不沉淀,下个客户重来 |

**实操翻译:** 这是 FDE 在阶段一(签约定成功标准)和阶段四(管理预期)最该掏出来的诊断工具。客户口中的"AI 落地",90% 实际只要 Sense+Understand(看板+问答),却按 Reason+Act(决策闭环)的预期付钱和排期——这是后期"怎么还没上线"冲突的根源。

**✅ 合格检查点:**
- 签约前,和客户**白纸黑字锁定交付落在第几层**(如"本期交付到 Reason,Act 做半自动试点"),而不是一句"AI 落地"。
- 每一层都有**可验收产物**(看板 / 问答准确率 / Evidence 覆盖率 / Decision Object 数 / 已执行 Action 数 / Eval 用例数),不是"做到了"三个字。
- 客户预期被对齐到"层级越高、工期越长、禁区越多"的现实——Act 层必然带审批和回滚,不可能"全自动下周上线"。

**💀 致命场景:** 销售按"决策闭环"(L4-L5)的愿景签了单,交付团队实际只能做到"问答"(L2),客户在第 35 天发现"AI 只会解释不会推动处置",信心崩塌。这正好踩中 `SKILL.md` 阶段四的试点疲劳陷阱——而根因在阶段一没把层级讲清。

> 和 KPI 四层的呼应:六层闭环回答"交付范围落在哪",`production-architecture.md` 的 KPI 四层回答"每层怎么量化"。两者正交,配合使用。

## 🧬 三、Ontology First:业务语义层是 AI 进入责任链的前提

**实操翻译:** 客户、合同、发票、设备、油井、工单、政策、指标,在不同系统里有不同字段、不同命名、不同口径。系统里存的是表、字段、文档、指标、日志、接口;业务人员问的却是"这个客户为什么高风险""这口井为什么停井"。**中间缺一层统一的业务语义。** 没这层,AI 只能在文本里找答案或现写 SQL,无法稳定理解"业务对象"和"对象关系",更不敢基于它做决策。

**Ontology(本体)不是画几张概念图,是企业 AI 的业务语义骨架。** 它至少要定义清楚:
- **有哪些业务对象 ObjectType**(客户、合同、发票、付款、设备、油井、故障、工单…);
- **对象有哪些属性 Property**(金额、状态、信用等级、逾期天数、风险等级…);
- **对象之间怎么关联 LinkType**(客户签合同、合同生发票、发票对应付款);
- **哪些规则触发判断 Rule**(逾期 15 天且未付超阈值 → 建议催收);
- **哪些动作可执行 ActionType**(建任务、发提醒、派单、审批、回写状态);
- (还有 Function / Event,分别承载可复用计算与时序事件)。

**为什么 Ontology 是前提,不是可选项:** 决策(Decide)和执行(Act)层的一切——证据检索、规则命中、Action 落锤、审计复现——都依赖"对象、关系、规则"被明确定义。本体缺失,后面四层全是浮沙。Palantir 把 Ontology 做成一等公民、而非数据字典附件,正是这个原因。

**📋 Ontology 成熟度评估清单(阶段一体检用,照着勾):**

| 成熟度 | 表现 | 对交付的含义 |
|---|---|---|
| L0 散落 | 对象/关系/规则全在人脑、Excel、会议纪要里 | 本体建设本身是工期大头,别按"接个 RAG"排期 |
| L1 文档化 | 有制度/SOP 文档,但不可执行、不可查询 | 需先做"文档→候选本体"的抽取+人工审核 |
| L2 半结构化 | 部分对象在系统里有表,但命名/口径不统一 | 需做数据到本体的映射+ co-bind(见下) |
| L3 一等公民 | 对象/属性/关系/规则/动作被系统化管理、可被 AI 直接读写 | 可直接进 Reason-Act,工期聚焦在场景闭环 |

**✅ 合格检查点:**
- 能指出该场景的核心业务对象(≥5 个)、它们之间的关键关系(≥3 条)、触发判断的规则(≥2 条),且这些**不是只存在 PPT 上,而是可被系统访问的数据结构**。
- 业务专家能看懂、能改、能署名(呼应阶段二"把经验沉淀为可执行资产,而不只是文档")。

**💀 致命场景:** 跳过本体直接搭 RAG/Agent,上线后发现"换个问法 AI 就答错",因为模型根本没稳定理解对象关系——查 bug 查到的是语义层缺失,补不动。

> 与现有 reference 的边界:本节是 `production-architecture.md`(架构)和 `mlops-playbook.md`(数据版本)都没覆盖的"业务语义"层。数据治理成熟(L2)≠ 本体成熟(L3)——前者解决"表干净不干净",后者解决"对象关系清楚不清楚"。

## 📦 四、Evidence Package 与 Decision Object:把"回答"沉淀成可治理对象

**实操翻译:** 传统 RAG 链路是「用户问题 → 文档片段 → LLM 总结」,产物是一段话。决策闭环要求更强的链路:「用户问题 → 识别业务对象 → 沿本体关系扩展路径 → 检索文档片段+映射来源 → 组织 Evidence Package → 生成可解释结论+推荐 Action」,产物是一个**可治理的对象**,而不是一次性聊天记录。

这是 `production-architecture.md`「trace 完备性硬标准」的**升华**:trace 解决"出事能查到是哪一步";Decision Object 解决"AI 的每一次结论,本身就是企业里一个可被引用、可被审批、可被复盘的资产"。

**Evidence Package 至少包含:** 命中对象、关系路径、文档片段、数据来源(哪张表/哪份文档/哪个字段)、映射事实、事件实例、置信度、权限过滤结果、推荐动作。它让 Agent 的输出从"我觉得"变成"基于这些对象、这些规则、这些证据,我建议这样做"。

**Decision Object(可治理决策对象)推荐 schema(给客户/法务能看懂的最小字段集):**

| 字段 | 含义 | 为什么必须有 |
|---|---|---|
| `targetEntity` | 这次决策针对哪个业务对象(如 Invoice INV-2026-001) | 决策要有明确主体,否则无法回写、无法追踪 |
| `reasoningPath` | 推理走过的对象关系路径 | 可解释性的骨架,审计时能还原"它怎么推到的" |
| `rulesMatched` | 命中了哪些规则(规则 ID + 名称) | 把"建议"钉在明文规则上,而非模型脑补 |
| `evidenceRefs` | 证据引用(文档片段/数据记录的指针) | 没证据引用的结论 = 不可审计 = 进不了责任链 |
| `recommendedActions` | 推荐动作列表(带风险等级+是否需审批) | 直接驱动 Act 层,呼应 `permissions-and-oversight.md` 的 A/B/C |
| `state` | 冴策状态(proposed/approved/executed/rolled_back) | 决策是有生命周期的对象,不是一句回答 |
| `traceId` | 指向完整 trace | 出事能 5 分钟定位根因(`production-architecture.md` 第四节) |

**✅ 合格检查点:**
- AI 的关键结论**每个**都以上述结构落库,不是只显示在聊天框里;`evidenceRefs` 为空的结论被系统标记为"低可信、不建议据此执行"。
- 审核人点开任一结论,能顺着 `reasoningPath` + `evidenceRefs` 一路点到原始材料那一行(呼应"破自动化偏见"招式一:禁一键通过、强制出处核对)。
- 一次决策出错,能用 `traceId` 在一个 trace 里还原全链路。

**💀 致命场景:** AI 给出"建议催收"但没有 `evidenceRefs`/`rulesMatched`,审核人无法核对依据,要么盲信(自动化偏见)、要么全盘否决(AI 价值归零)——决策对象设计缺陷直接废掉整个 B 类价值区。

## ⚙️ 五、可治理 Action 生命周期(呼应禁区,不重复)

**与 `permissions-and-oversight.md` 的分工:** 那个文件回答"哪些操作 AI 不能碰、agent 权限怎么收、审批门怎么设";本节回答"一个被允许执行的 Action,作为企业里的一等公民,它的**完整生命周期**长什么样"。两者互补,不重复。

**Action 生命周期(每个 Action 都要走完,缺环即风险):**

```
Propose(提议) → Validate(校验签名/权限/幂等) → Approve(按风险分级审批)
   → Execute(执行,留审计) → Verify(验证副作用是否如预期)
   → Audit(审计留痕) → Rollback/Compensate(失败可回滚或补偿)
   → Update Ontology(执行结果回写对象状态)
```

**每个 Action 必须带的"治理元数据"(立项时就锁定):**
- **明确签名**(入参/出参/副作用说明,不能是个黑盒函数);
- **权限要求**(谁能提议、谁能审批、谁能执行——三权分立);
- **审批策略**(A 类自动 / B 类抽审 / C 类强制人落锤,见 `permissions-and-oversight.md`);
- **幂等键**(同一个 Action 重复执行不产生重复副作用,防重放/防 agent 死循环);
- **回滚或补偿机制**(执行失败后怎么退回——能退的 rollback,不能退的 compensating action);
- **审计记录**(who/what/when,不可篡改)。

**✅ 合格检查点:**
- 场景里的每个 ActionType 都能填出上面六项元数据;填不出"回滚/补偿"的,自动归为 C 类(人落锤,不给 AI 执行接口)。
- 一次执行失败,能在审计里看到完整生命周期(提议→审批→执行→失败→补偿),而不是只剩一条"执行报错"日志。

**💀 致命场景:** Action 没有幂等键,agent 重试时把同一笔催收任务建了三次;或没有补偿机制,执行了一半失败,业务状态卡在中间,无法回滚也无法继续。

> 与"危险操作审批门 + 预算熔断"的关系:那是"防 agent 乱来"的闸;本节是"Action 本身作为可治理对象"的骨架。两者叠加才是完整的 Act 层。

## 🤖 六、受控 Agent 自治等级 L0–L3(呼应权限四打法,不重复)

**与 `permissions-and-oversight.md` 的分工:** 那个文件回答"agent 权限怎么收(default deny / 身份化 / 读写分离 / 熔断)";本节回答"**这个 agent 该被允许多自主**"——一个正交的维度。权限收得再紧,自治等级定错了照样出事(反之亦然)。

**自治等级(决定 agent 能"自己走到哪一步"):**

| 等级 | 自治度 | 典型边界 | 适用 |
|---|---|---|---|
| **L0 仅感知** | 只读、只建议,不起草任何 Action | 看板、解释型问答 | 高风险场景的起点 |
| **L1 起草待审** | 可起草 Action Proposal,但**必须人审批才执行** | 默认推荐等级 | 绝大多数 B 端场景的合理起点 |
| **L2 有限自动** | 低风险动作自动执行,高风险仍待审 | A 类自动、B/C 类待审 | 流程稳定、监控完善后 |
| **L3 高度自动** | 端到端自动,人只看异常 | 极少;仅低风险、可挽回、有强监控 | 很少见于严肃行业 |

**实操翻译:** 企业落地 AI 的合理节奏是**默认从 L1 起步**:先给建议、必要时起草 Action,由人确认后执行。这比"让模型直接全自动"更符合企业真实落地节奏,也正好对齐 `permissions-and-oversight.md` 的 B 类(建议+审核)。盲目冲 L3 是最常见的越界——agent 越强,L3 的风险越大。

**✅ 合格检查点:**
- 每个 agent 有显式标注的自治等级,且 L2+ 必须满足"L1 已稳定运行 + 监控完善 + 有熔断"三项前置。
- 没有任何 agent 默认是 L3;L3 必须逐项论证"错了能挽回、能熔断、能审计"。

**💀 致命场景:** 跳过 L1 直接给 agent L3 自治,某次推理偏了直接落锤了一个本该人审的操作,且没有熔断——一次事故清零信任。

## 🧰 七、行业 Pack:从"每次重做"到"平台内核 + 资产复用"

**实操翻译:** 很多 AI 项目"demo 很快、复制很慢"的根因是:经验没沉淀成可复用资产,下个客户、下个场景又要重新梳理本体、规则、Action。**FDE 的长期价值,不只是交付一个客户,而是把现场打法沉淀成行业 Pack。**

**一个 Pack 可以包含:** 行业本体模板、连接器、知识包、Agent 模板、Action 模板、决策流模板、Eval 数据集。

**对阶段四(预期管理)和报价的直接含义:**
- 第一个客户:本体/规则从 0 建,工期长、价格高(买的是"陪你蹚一遍")。
- 第二个客户起:复用 Pack,本体草稿构建周期可大幅缩短(行业实践常报 80%–90%+),报价和工期应相应调整——**别按"第一个客户"的工时给后续客户报价**,否则要么贵得丢单、要么便宜得做亏。
- Eval 数据集是 Pack 里最容易被忽略、却最值钱的部分——它让"准确率"从口号变成可回归比对的基线。

**✅ 合格检查点:**
- 每交付一个场景,至少沉淀出:可复用的本体片段 + ≥1 个 Action 模板 + ≥1 套 Eval 用例。做不到 = 这个项目做完没给组织留下资产。
- 报价模型区分"首次场景建设"与"Pack 复用交付"两种模式。

**💀 致命场景:** 做完三个客户,每个都从零搭本体,团队累死、利润摊薄、还做不出壁垒——典型的"做项目不做产品"。

## 📁 八、三个真实场景案例

> 这三个案例改编自 NEXA Decision OS 等同类系统的公开场景描述,适合提炼"决策闭环怎么落地"的工程经验。记牢它们,是为了在客户抛出类似场景时,能立刻拆出"对象/关系/规则/证据/Action/产物"六件套,而不是空谈。

### 案例一:企业经营决策 ——「这张发票为什么建议催收?还能做什么?」

- **业务问题:** INV-2026-001 为什么建议启动催收?有哪些替代处置?
- **本体对象:** Invoice(发票)→ 关联 Customer(客户)/ Contract(合同)/ Payment(付款)/ Policy(政策)。
- **证据链:** 事实(逾期天数、未付金额、信用等级、账期)+ 文档证据(合同条款、付款记录、政策规则、数据映射来源)。
- **规则命中:** 如"逾期 ≥15 天 且 未付 ≥ 阈值 且 信用等级 ≤ X → 建议催收"。
- **Action:** 审批后调用工具创建催收任务、回写发票状态、留审计。
- **可治理产物:** 一个 Decision Object(target=INV-2026-001, reasoningPath, rulesMatched, evidenceRefs, recommendedActions=[催收/提醒/升级审批/暂停授信], state, traceId)。
- **🧭 FDE 评估启示:** 这是典型的 L4 Decide 场景。关键卡点不在模型,而在**合同/付款/政策数据能不能映射到统一本体**——本体没建好,Evidence Package 拼不出来,决策对象就是空壳。阶段一体检重点查"发票-合同-付款-政策"四对象的关系在客户系统里是否可追溯。

### 案例二:能源运维 ——「渤中 26-6-A12H 为什么建议调整泥浆密度?」

- **业务问题:** 某口井为什么建议调参?调了能不能回退?
- **本体对象:** Well(井)→ 关联 Field(油田)/ Block(区块)/ Equipment(设备)/ Fault(故障)/ ProductionRecord(生产记录)/ Monitoring(动态监测)。
- **证据链:** 井控规程文档 + 实时 ECD(当量循环密度)曲线 + 邻井溢流路径(图关系)。
- **推理类型:** Rule + Graph + Temporal 混合推理(规则命中 + 图路径扩展 + 时序趋势),综合置信度。
- **Action:** 生成带**回滚策略**的调参候选(调参是可逆的,但仍建议人审——井控不可逆后果多)。
- **可治理产物:** Decision Object + 两条 Action 候选 + Evidence Package + Trace 全程可追溯。
- **🧭 FDE 评估启示:** 能源/井控是**强禁区**场景(见 `permissions-and-oversight.md` C 类:解除安全联锁 = 不可逆)。即便 Action 可回滚,自治等级也应压在 L1(起草待审),绝不上 L3。多模态证据(图表/曲线)纳入证据层是后续增强点。

### 案例三:数据治理 ——「这张核心表为什么质量评分下降?该谁处理?」

- **业务问题:** 质量异常的根因 + 责任人 + 处置动作。
- **本体对象:** DataAsset(数据资产)/ Field(字段)/ Standard(标准)/ QualityRule(质量规则)/ Lineage(血缘)/ Owner(责任人)/ GovernanceTask(治理任务)。
- **证据链:** 质量规则命中 + 血缘(影响哪些下游)+ 责任人映射。
- **Action:** 解释异常来源 → 找到影响下游 → 推荐治理规则 → 生成治理任务 → 进审批 → 调用治理平台/工单系统 → 留执行审计。
- **可治理产物:** 让数据治理从"发现问题"进入"治理执行闭环"——这正是数据治理平台最缺的一环。
- **🧭 FDE 评估启示:** 数据治理客户常已有数仓/BI/治理平台,FDE 的价值不是替换它们,而是**用本体把它们连成决策闭环**(呼应下文 Palantir"连接而非替换")。阶段三要重点回答"AI 输出能不能接进现有工单/治理系统",接不进 = 价值停在 L2。

### 一句话总结这三个案例
**发票催收告诉你:本体不建好,Evidence 拼不出来;油田井控告诉你:可回滚 ≠ 可全自动,禁区场景压低自治等级;数据治理告诉你:连接已有系统比替换它们更现实。**

## 🏛️ 九、Palantir 启发与边界:借鉴什么、不照搬什么

**借鉴什么(对 FDE 有方法补强的产业共识):**
- **企业 AI 必须围绕"业务对象"组织,而不是围绕"文档段落"。** 这是 Ontology First 的产业验证。
- **企业 AI 的输出必须能沉淀为可治理的决策对象,而不只是一次性回答。** 这是 Decision Object 的价值。
- **企业 AI 不能绕过权限、审批、审计去调工具。** 这和 `permissions-and-oversight.md` 三条禁区线完全同向。
- **企业 AI 的核心资产不是单个 prompt,而是「本体 + 证据 + Agent + Action + Trace + 行业 Pack」。** 这定义了交付的真正护城河。
- **"控制面可上云、数据面不出域"的混合部署** 在金融/医疗/政企是刚需(见 `production-architecture.md` 第五节)。

**不照搬什么(避免把方法论变成采购清单):**
- **不绑定某个具体产品/版本。** skill 提炼的是可复用思想,不是某个 OS 的功能清单或版本路线图。客户用什么技术栈不重要,重要的是这五层(Ontology/Evidence/Agent/Action/Audit)有没有被建出来。
- **不把"上 Decision OS 平台"当成前提。** 很多场景用轻量组合(现有数仓 + 本体草稿 + GraphRAG + 受控 Agent + 审批流)就能跑通 L1-L4,不必一上来就铺大平台。FDE 的工作方式是"先做一条高价值闭环的最短路径"(呼应 `production-architecture.md` 决策原则)。
- **不替代现有 reference,只补强。** 本文件是"业务语义+决策闭环"这一层;权限、MLOps、架构、KPI 仍以各自 reference 为准。

---

> **一句话收尾:企业不缺数据,也不缺模型,真正稀缺的是把数据、知识、规则、对象、Agent、Action、审计串成可治理闭环的那层工程判断。FDE 的专业度,很大一部分体现在能判断"客户的 AI 到底进没进业务责任链"——进不去的,模型再强也只是个会聊天的助手。**
