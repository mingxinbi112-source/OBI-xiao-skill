# AI B 端 FDE 交付评估工作流

> FDE(Forward Deployed Engineer) 从现场到钱箱的 AI 企业级交付方法论:四阶段工作流 + Go/Hold/No-Go 评估关卡 + 14 个 references playbook 深入展开。

## 何时使用

凡涉及 AI 在企业/工厂/医院/银行/政企的落地、交付、评估、上生产、权限边界、KPI、合规、决策闭环,以及 FDE 小团队自身的组建与生死,即可触发本 skill。具体的触发关键词与分场景说明详见上方 `description` 与文末「深入资源」。

## 这个技能在解决什么

B 端 AI 项目几乎从不是死于模型不够强,而是死于三件事:

1. **握有隐性知识的老员工软抵制** —— 模型再准,没人喂真实数据、没人愿意改流程,就是空中楼阁。
2. **PoC 之后的工程化与 MLOps 鸿沟** —— 95% 的项目死在漂亮的 demo 之后,死在集成、可靠性、合规这"最后一公里"。
3. **第 35 天的试点疲劳与信心崩塌** —— 客户在"水面下 60% 脏活"的视线盲区里失去耐心。

这套方法论把这三件死因,转成一条**可执行、可验收、每阶段都能 Go/No-Go 判定**的交付工作流。它既是 FDE(Forward-Deployed Engineer)的操作 SOP,也是一套评估框架——你可以用它给任何一个 B 端 AI 项目打分,判断它该不该签、该不该上生产、卡在哪一公里。

## FDE 的根本定义:从现场到钱箱的脏活闭环

上面三件死因回答"项目为什么死";但 FDE 还要回答更根本的一件事——**怎么从客户的真实工作里,跑通一个有人愿意付钱的闭环**。一句话:

> **FDE = 从现场到钱箱的脏活闭环**:扎到客户干活的一线(现场),找到他真正头疼的繁琐问题(脏活),做出能帮他解决问题的东西,并让他愿意为结果付钱(钱箱),从头到尾一步都不能断(闭环)。

这条闭环用三个乘法公式丈量,任何一项接近零,最后价值就接近零。它们是贯穿四阶段全程的诊断器——项目卡住时,逐项排查哪一乘项塌了:

- **FDE 结果 = 真问题 × 可用结果 × 进入工作 × 持续使用** —— 问题不真、结果不能用、没进入工作、或只打开一次,前面做得再漂亮价值都接近零。
- **采用 = 看得懂 × 信得过 × 不麻烦 × 有下一步** —— 客户不用时别先怪"不懂 AI",先查是不是把麻烦都留给了客户。
- **真需求证据 = 具体角色 × 最近事件 × 当前做法 × 明确后果 × 真实材料 × 付费角色** —— "客户说想要"是解决办法不是证据;任一项说不清,先回去补。

> 这条"现场→钱箱"视角,补的是四阶段(偏乙方交付工程化)的上游和下游:**怎么从现场找到真问题、验证有人愿意付费,以及怎么把多次交付沉淀成产品**。完整的七步责任链、做窄做深的最小闭环、商业证据阶梯、产品化沉淀(三堆法 / 0→1·1→10·10→100 / 载体选择阶梯)、价值分配、六个教练式 Prompt、七天行动卡、红队检查,见 `references/field-to-cashbox-playbook.md`。

## 核心铁律(贯彻全程)

- **技术再强,也得有人配合。** 落地不取决于模型多好,而取决于能否搞定握有隐性知识、可能产生软抵制的一线老员工。
- **永远不被漂亮的 PoC 欺骗。** 把"能不能 demo"和"能不能上生产"当作两个完全不同的问题。
- **交付的核心是预期管理。** 用坦诚的体检和有节奏的"不性感进展",对抗客户最容易崩盘的信心周期。
- **真正值钱的本事是会"划禁区",不是会"用工具"。** 知道哪些事 AI 碰都不该碰——不可逆决策拍板、绕过有效人工审核、agent 越权操作——比让它多干一点活重要得多。AI 错的时候特别自信,一次本可避免的严重错误就足以让严肃行业整套弃用这套系统。划禁区表面是设限,本质是保护系统能长久活下去、被一直信任。
- **复杂度优先放路由,不堆 agent 数。** 别一上来就搭层层 agent hierarchy——Klarna 用单 agent + 强路由扛起 230 万次对话/月、三分之二客服量。先把系统拆成控制面(计划/路由/审批)和执行面(检索/推理/工具),能单 agent + 强路由解决的就不上多 agent,能确定性 pipeline 解决的就不上 agent。架构上的克制,和权限上的克制是同一件事。
- **AI 止于"会回答" = 失败,必须能进入业务闭环并沉淀为可治理的决策对象。** 企业 AI 的真正跃迁是从"解释器和助手"走到"参与决策、推动处置"。而能进入业务闭环的前提,是业务语义(Ontology:对象/属性/关系/规则/动作)先被统一——否则 AI 只能在文本里找答案或现写 SQL,不敢也不该被放进业务责任链。客户说"要 AI 落地"时,先用「Sense→Understand→Reason→Decide→Act→Learn」六层闭环逼他定位到底要落到哪一层(看板 vs 决策闭环,工期差一个数量级)。详见 references/decision-os-playbook.md。
- **抽象是工程师的活,专家只负责实操和判对错。** 落地 FDE 最先撞的墙,是专家"只能实操、无法抽象"——这是隐性知识的本质(Polanyi:我们知道的比能说出来的多),不是专家的缺陷。逼专家写 SOP 必然失败(要么正确的废话,要么脱节教科书)。正确的 SOP 是「触发→判据→动作→例外」的决策树,不是「第一步、第二步」的步骤流水——而例外条款,往往占专家真实水平的一半以上。让专家保持在"判对错"的位置,永远别把他推到"归纳/创造"的位置。详见 references/expert-knowledge-extraction.md。
- **FDE 不做瀑布,做贪吃蛇。** 闷头做三个月再上线,项目大概率死在第六周——甲方看不到东西就怀疑、抽人、砍预算。第 2-3 周就必须交出一个能用的薄切片(范围窄、专家每天都被烦、判据相对清晰的子环节,覆盖 10% 也行),它的作用不是产生多少价值,而是买时间和信任;之后每两周滚动一个新切片,把季度大重构拆成 6-7 个两周小胜利。薄切片一半给甲方信号,一半破专家抵触(先帮他干脏活)。节奏和政治是耦合的——首月必须同时拿下甲方信任和专家配合两张牌。详见阶段四 land-and-expand 与 references/expert-knowledge-extraction.md。
- **做窄做深,不是少做一点。** 第一版从一整个真实现场(二三十个节点)里只选最关键的一两个节点,再把这一个节点从真实输入做到账面可核对、工作里可使用。窄解决范围,深解决价值——把有限时间全打在最关键的一个点上。两个节点只有属于同一条问题链、能被同一份核心材料和同一轮验证串起来,才允许一起做。最小闭环五步链(真实输入→AI 一步→可核对结果→下一动作→反馈信号)见 references/field-to-cashbox-playbook.md。
- **商业证据不能跨级庆祝。** 称赞→继续聊→给真实材料→真实使用→首次付费→复购扩展→经营改善,是一组**客户承担成本递增**的阶梯。愿意给材料≠已采用,使用过一次≠持续使用,付过一次钱≠已续费,更≠经营结果已提升。哪一级没有证据,结论就停在哪一级——别用低层证据替代高层结论。这条阶梯和 land-and-expand 配套:薄切片买到的是"继续聊/给材料"层级的证据,真正续命要推到"真实使用/付费"层级。
- **先让客户得到 100 的价值,再讨论你拿 5。** 想收客户的钱,先让客户得到一笔看得见、算得清的价值(降本/增效/增收)。说不清客户少花了什么钱、省下什么时间、增加什么收入,客户就很难判断为什么要付钱。收费方式(试用费/项目费/订阅/结果分成)放在价值之后讨论;按结果分成只在结果、基线、归因、数据口径都说得清时才适合。
- **交付不是终点,激活才是起点;NRR<100% 即价值蒸发。** scorecard 判 Go、系统上生产,只是入场券——签约后 90 天的激活(把"能跑的系统"变成"客户每天离不开的资产")才是 FDE 价值的真正起点;激活之后还有续约(守住 NRR、防五类流失)、扩收(把价值变成钱)、规模化(一个客户成功变一类客户成功,**定制递减率是 FDE 模式成立的试金石**)。没有"做完就走",只有"价值持续可证"。详见 `references/activation-playbook.md` / `renewal-and-expansion-playbook.md` / `scaling-playbook.md` + `fde-metrics.md` 四层指标。
- **G 端不是小号的 B 端:先过市场级四关,再谈项目级体检。** 政府/国企客户的交付工程可以与 B 端同构,但钱袋结构(财政口袋年年重招 vs 省钱口袋合同即多年)、采购名目(复购·资产·名目·真用四关)、验收死法(驻场人力运维/纯大屏/总包分包)完全不同——选错城、选错场景,交付做得再对也是死。活地三信号选城、四关过滤器、收入硬度光谱、死亡雷达见 `references/gov-smartcity-playbook.md`。
- **1-3 人小团队:决策门之上还有生存门。** scorecard 满分的 Go 项目,踩中硬轨红线(应收>4 月固定成本/账上<6 月跑道碰垫资单)照样不接;该不该扩张看吸收率(人力需求=交付总量×(1−吸收率)),不看在手订单;每个切入赌注预注册 90 天三道处决门(D30 现场门/D60 合同门/D90 资产门),事后不许挪;权属条款写合同第一页,遗产三件套保证合同死、资产不死。团队选拓扑与处决纪律见 `references/small-team-playbook.md`。

## 工作流总览

四阶段,顺序执行,每阶段结尾有一个 **🚦 Go / Hold / No-Go 评估关卡**——不通过不进下一阶段。这是把"交付工作流"和"评估"焊在一起的关键设计。

| 阶段 | 目标 | 核心动作 | 评估关卡 |
|---|---|---|---|
| 一、签约前残酷体检 | 在最便宜的阶段筛掉死局 | 数据/集成/人际/成功标准四维排查 | 🚦 决定签不签 |
| 二、人际破局 | 把潜在敌人变成功臣 | 话术重构 + 荣誉绑定 + 痛点降维 | 🚦 决定推不推进 |
| 三、MLOps 并行架构 | 搭让 AI 在生产活下去的骨架 | 人机边界 A/B/C + 审核防自动化偏见 + Agent 权限禁区 + 六大骨架 | 🚦 决定上不上生产 |
| 四、预期管理 | 挺过第 35 天信心崩塌期 | 预防针 + 不性感里程碑 + 两周快跑 + 反向承诺 | 🚦 决定续不续命 |

完整带权重与分数阈值的量化打分表见 `references/scorecard.md`。

### 🚦 两类门:决策门(事前) vs 运营门(事后)

> **关键防逻辑断裂:** 四阶段 Go/Hold/No-Go 是**决策门**(事前,scorecard 打分,35/20/30/15 权重**完全不动**)——回答"这仗该不该打、能不能上生产"。但**签下单、上了线,都不是终点**:Go 只是运营门的**入场券,不是终点**。交付之后还有一整段生命周期,由**运营门**(事后,fde-metrics 度量)覆盖:

| 运营门阶段 | 回答的问题 | 主战场 reference |
|---|---|---|
| **激活部署**(签约后 90 天) | 上线 ≠ 被用——把 demo 变成客户离不开的资产 | `references/activation-playbook.md` |
| **续约 + 扩收** | 守住 NRR(及格 100% / 优秀 120%)+ 把价值变成钱 | `references/renewal-and-expansion-playbook.md` |
| **规模化复制** | 一个客户成功 → 一类客户成功(复用率 / 定制递减率) | `references/scaling-playbook.md` |
| **四层指标中枢** | 做得怎么样(交付 / 客户 / 商业 / 组织层读数) | `references/fde-metrics.md` |

> **两类门性质不同,绝不对运营门套 Go/No-Go 打分**——运营门不给"上线 / 不上线"的判罚,只给"现在哪里在生病、该往哪个方向干预"的读数。一个评分 Go、上了生产的项目,完全可能因激活失败、价值蒸发而最终 NRR<100%。**决策门管"做不做",运营门管"做得怎么样"——前者是资格,后者是成绩。**

### 七步责任链 ↔ 四阶段映射(现场→钱箱视角 与 交付工程化视角对齐)

案例的"现场到钱箱"七步,和本技能的四阶段是同一件事的两个视角——七步偏产品化验证(从找问题到付费),四阶段偏乙方交付工程化(从签约到上生产)。两者这样对齐:

| 案例七步(现场→钱箱) | 落在 | 四阶段里对应的事 |
|---|---|---|
| 1. 进入现场(最近事件 + 授权材料) | 阶段一 | 必查①数据成熟度(强制 3-5 真实样本)+ 进入现场三件事 |
| 2. 发现问题(谁卡住、损失什么、怎么补救) | 阶段一 | 必查③人际利益 + ④成功标准 + 真需求卡 |
| 3. 定义范围(一个用户/输入/结果/下一步) | 阶段一/二 | ⑤六层闭环定位交付层级 + 做窄做深(只抓 1-2 节点) |
| 4. 共同搭建(业务交材料/标准/验收/下一动作) | 阶段二 | 抢救隐性知识 + 荣誉绑定 + 最小闭环五步链 |
| 5. 部署工作流(结果何时交谁、下一步做什么) | 阶段三/四 | 控制面/执行面 + land-and-expand 薄切片上线 |
| 6. 促进采用(看得懂/信得过/不麻烦/有下一步) | 阶段三/四 | 人机边界 A/B/C + 审核防自动化偏见 + 采用四道门 |
| 7. 验证影响(谁用了/改了/付费/复购) | 阶段四 | KPI 四层 + 商业证据阶梯(不跨级庆祝) |
| (再绕一圈)现场反过来改产品 | 贯穿 | 行业 Pack 复用 + 三堆分类法 + 载体选择阶梯 → 打法手册三属性 + 三级杠杆(详见 `scaling-playbook.md`) |

七步的过关信号、两条闭环、做窄做深、商业证据阶梯、产品化沉淀的完整展开见 `references/field-to-cashbox-playbook.md`。

## 阶段一:签约前"残酷体检"与死局筛查(Pre-signing Audit)

**目标:** 在最便宜的阶段(还没投入团队)筛掉死局。这一阶段省下的,是后面几个月的沉没成本。

### 进入现场:体检的前提(把"客户"拆成四种角色 + 真需求卡)

四维排查之前,先确认你真的"在现场"——现场不是必须去线下,而是一件真实业务正在发生、有人做判断、有人承担结果的工作链。判断有没有进入现场,看三件事:① 能不能看到最近一次真实事件?② 能不能拿到一份合规、获授权的材料?③ 结果出来以后,能不能继续追到下一步?三件都能做到,即使全程在线也在现场。

然后,把一句含糊的"客户"拆成四种角色——**分不清他们,就不知道谁该提供材料、谁核对结果、谁执行下一步、谁愿意付钱**:

| 角色 | 是谁 | 在四阶段里对应 |
|---|---|---|
| **使用者** | 提交材料、查看结果的一线人 | 阶段二的隐性知识持有者(必查①③ 的真实样本来源) |
| **受益者** | 希望结果改善自己处境的人(如顾客) | 成功标准里的最终价值对象 |
| **决策者** | 能让这件事进入日常工作的人 | 接触一线的入口、IT 审批推动者 |
| **付费者** | 最后判断是否值得持续投入的人 | 成功标准与预算的拍板人 |

最后,把排查收成一张**真需求卡**(七项必须具体):具体角色 / 最近事件(哪天哪步发生什么) / 当前做法(现在怎么绕、为何仍不够) / 明确后果(不解决损失什么) / 已有投入(时间人力流程数据钱) / 真实材料(哪份获授权可脱敏) / 下一次验证(七天只做哪个动作补证据)。**只有观点没事件、只有痛点没后果、只有想法没材料——任一项先不过**。真需求证据公式见上方「FDE 的根本定义」。

---

### 必查四维(每维都有可量化标准)

**① 数据成熟度**
- 数据是活在系统里(库表/API/日志),还是散在老员工脑子里或 Excel?
  - 量化红线:**必须强制客户提供 3-5 个真实样本**。爽快给 = 绿灯;支支吾吾、要"走流程审批两周才给" = 黄灯甚至红灯。客户对真实数据的态度,就是项目成败的预告片。
- 数据有没有明确 Owner?维护频率?(没人维护的"死数据"是定时炸弹)
- 法律合规边界在哪?(医疗/金融/政企的个人信息、数据出境、训练授权)

**② 系统集成度**
- 核心系统多老旧?有没有 API 文档?
- 改动系统要走多久 IT + 合规审批?
  - 量化红线:审批 > 8 周 = 高风险;> 6 个月 = 接近死局。
- AI 的输入/输出能不能真正接进业务流,还是只能做成"旁边一个网页"?

**③ 人际与利益博弈**
- 这个 AI 到底动了谁的流程、谁的"饭碗"?
- 能不能直接接触到每天使用它的一线员工?(被中间管理层隔离 = 隐患)
- 利益受损方在决策链里的权重有多大?

**④ 成功标准定义**
- 拒绝"提升效率""降本增效"等模糊词。
- 必须量化、可验收:如"将人工初审时长从 X 分钟降到 Y 分钟,Z% 的 case 自动通过,准确率 ≥ N%,月节省 W 工时"。
- 必须有 Plan B(指标达不到时的退路)。
- **KPI 至少分两层锁:** 业务层(adoption/完成率/人工替代率/成本改善)+ 质量层(准确率/复核通过率/路由正确率);系统层与数据层指标在阶段三补齐。企业真正认的是 adoption 和单位产出,不是模型 benchmark。四层 KPI 体系见 `references/production-architecture.md`。

### ⑤ 交付范围与业务语义诊断(决定工期量级)

前四维回答"能不能签";这第五维回答"签下来要做多深、工期大概什么量级"。它常被销售和客户双方都跳过,是后期"怎么还没上线"冲突的根源。

- **交付范围用六层闭环定位:** 客户口中的"AI 落地",到底只要 Sense+Understand(看板/问答,1-2 周到 1-2 月),还是要 Reason+Decide+Act(决策闭环,3-6 个月起)?**白纸黑字锁定交付落在第几层**,而不是一句"AI 落地"。每层要有可验收产物(看板 / 问答准确率 / Evidence 覆盖率 / Decision Object 数 / 已执行 Action 数 / Eval 用例数)。
- **业务语义(Ontology)成熟度:** 这个场景的核心业务对象(客户/合同/发票/设备/工单…)和它们之间的关系、规则,是已系统化(L3 一等公民),还是散在文档/Excel/人脑里(L0 散落)?散落程度直接决定本体建设工期——别按"接个 RAG"排期。Ontology 成熟度四级评估表见 `references/decision-os-playbook.md`。

> **避坑:** 销售最容易被客户的"做个 AI 决策系统"带着走,默认按决策闭环(L4-L5)的愿景承诺、按问答(L2)的工期排期。FDE 必须在签约前把层级讲死,否则第 35 天必然冲突。

> **避坑(乙方自检):交付方有没有"内核平台"?** Palantir FDE 能几周交付,靠的是 80% 能力平台已现成(Foundry/Gotham),FDE 只在最后一公里做适配。**没有内核,FDE 就退化成"高级驻场外包"——每个项目从零堆人日,做十个客户成本是十倍,规模不经济。** 签约前自问:这个项目沉淀的专家知识/规则/Action 模板,能不能复用到同行业下一个客户(形成"行业 Pack")?能 = 有杠杆(先亏前几个客户、第 N 个开始赚钱);不能 = 纯人日生意,报价必须够覆盖全量理解成本,别按"可复制"幻想报价。AI 大模型把"抽业务逻辑"的成本砍了一个量级,正是补内核缺口的杠杆——但前提是你真把抽出来的知识沉淀成可复用资产(见 `references/decision-os-playbook.md` 行业 Pack + `references/expert-knowledge-extraction.md`)。

### 🚦 阶段一 Go / Hold / No-Go

- **GO(可签):** 真实样本爽快给出 + 数据有 Owner + 核心系统可接(IT 审批 ≤ 8 周)+ 成功标准已量化且有 Plan B + 能接触一线。
- **HOLD(补课后再签):** 部分维度不达标。补救动作:先做一个 1-2 周的"数据可用性 mini 验证",拿到样本和 Owner 承诺再签。
- **NO-GO(死局,建议放弃或重构范围):** 数据在脑子里/Excel 且客户不愿给样本 + 核心系统封闭无文档且审批 > 6 个月 + 动了强势利益方饭碗且无法接触一线 + 成功标准无法量化。

> **避坑:** 销售最容易在阶段一帮客户"粉饰"。FDE 必须亲自要样本、亲自问 Owner、亲自走一遍 IT 审批流程模拟,不要听转述。

> **操作化工具:** 阶段一落在 HOLD 时,需要把"先做个 mini 验证"真正跑起来;或当客户提到"数据本地化/私有化/信创"等模糊词、需要逼出具体档位时,用签约前体检工具箱(四档本地化分法 + 一周 mini 验证 SOP + 样本索取话术 + 口径梳理工作表)——见 `references/pre-signing-audit-toolkit.md`。

## 阶段二:人际破局与"抢救隐性知识"(Human-Centric Strategy)

**目标:** 把潜在的"软抵制敌人"转化为"项目功臣"。这一阶段做不好,后面所有工程都是零。

### 三大动作

**① 话术与定位重构(严禁"替代"字眼)**
对一线老师傅,开场定调为"抢救、保存、传承"他几十年不熄的手艺,而不是"用 AI 替代你"。让他感到的是最高尊重,而不是被榨取。

**② 利益与荣誉绑定**
- 把 AI 的判断逻辑**冠名**,如"X 师傅经验模型""X 工艺知识库"。
- 向管理层汇报时,把他包装成项目的**核心功臣**,而不是被采集的"素材"。
- 让他在系统里有署名、有审核权、有"我的经验被沉淀了"的、可向同事炫耀的成就感。
- **把他的经验沉淀成可执行资产,而不只是文档。** 最高级的荣誉绑定,是把他的判断逻辑结构化成本体对象(业务对象/属性/关系)、业务规则、Action 模板——这些是能被系统直接调用、能复用到下一个场景的资产,而不是又一份落灰的 SOP。这同时呼应 Ontology First:隐性知识不沉淀进本体,决策闭环就是空中楼阁。详见 `references/decision-os-playbook.md`。

**③ 魔法级痛点降维打击**
- 找出他日常最烦、最无价值的重复性杂活(填表、抄录、对账、归档、查档)。
- 用 AI 先帮他**干掉这些杂活**,让他第一周就尝到甜头。
- 先给甜头,再谈沉淀核心知识。顺序不能反。

### ④ 专家配合的五种结构性机制 + 专家类型诊断

「三大动作」是话术层和荣誉层;但**靠情怀换不来秘密**——你等于在专家面前组装一台"替换我自己"的机器,从他的利益看,认真配合你是非理性的。**必须动结构。** 五种机制,按"撬出隐性知识的力度"从弱到强:

1. **上级硬性授权 + KPI 绑定(底线但最弱)** —— 有强制力但撬不出隐性知识,换来的是物理在场、精神缺席。单用必败,必须叠加下面几条。
2. **重新定义角色(从干活变定规矩)** —— "这套系统署您的名,全公司新人都按您定的规矩干",让他意识到知识被沉淀是**放大而非替换**(判断力从覆盖自己的单子,变成覆盖整个部门)。这是动作②「荣誉绑定」的底层逻辑。
3. **先帮他干掉最烦的脏活(先给糖,再要秘密)** —— 第一个切片别碰核心机密判断,去替他干填表/跑数/抄录。他尝到甜头,防御心才松。顺序不能反。
4. **直接的利益绑定** —— 项目奖金/专家分成/知识产权署名,且必须**书面**。SOP 跑得越好他拿得越多,才会交出压箱底的例外条款。
5. **接受撬不出 100% + 不依赖单个专家(最强谈判杠杆)** —— 总有专家战略性保留最关键的 20%。对策不是死磕一个人,而是横向找 2-3 个专家交叉验证——当他发现"这套东西没我也在往前走",反而会主动补全。**降低对单一专家的依赖,本身就是最强的谈判杠杆**(与阶段一"必须多元数据样本"同构:单点依赖=单点要挟)。

**先诊断专家类型,再出牌:** 职业荣誉型→先出机制 2;打工型(KPI/钱驱动)→先出机制 4+1;防御型(明显保留、话只说一半)→先用机制 5 打破单点 + 机制 3 降防备;濒临退休型→机制 2(署名传承)。**诊断时机:阶段一面见专家时就做**(见 `references/pre-signing-audit-toolkit.md` Day 3)。误判代价很大:对打工型空谈荣誉=画饼,对荣誉型直白谈钱=冒犯。五种机制详解与专家类型诊断表见 `references/expert-knowledge-extraction.md`。

### ⑤ 隐性知识抽取 SOP:写决策树,不写步骤流水

专家"只能实操、无法抽象"是隐性知识的本质(Polanyi),不是缺陷。**第一条铁律:不要指望专家做抽象——抽象是工程师的活,专家只负责实操和判对错。** 逼专家写 SOP 必败(正确的废话或脱节教科书)。正确做法是**工程师抽、专家"改"**:

- **不问"你怎么做",抓"你在哪停顿"** —— 影随 + 出声思考(think-aloud),停顿点/皱眉/回头核对的瞬间就是决策点;关键决策法(CDM)让他回忆一个非典型案例;对比反例法逼出隐藏规则。
- **专家术语 = 被压缩的判据** —— "感觉不太行"要追成"客户类型 × 账期阈值 × 历史违约"的可判定规则(逼问"看着像但不算"的边界是钥匙)。
- **SOP 写成"触发→判据→动作→例外"的决策树** —— 例外条款往往占专家真实水平一半以上,没有例外的 SOP 等于把专家降维成新人。
- **闭环验证:让专家"改"不让"写"** —— 故意不完美的初稿当诱饵,他改出来的修改点就是漏抽的隐性规则。AI 可起草初稿/聚类录屏/构造边界case,但**判对错的最终权必须在专家手里**(否则把偏见和智慧一起学进去,沉淀出一套自信的错误)。

抽取三手法、术语解压缩逼问链、决策树四要素表、闭环验证流程、配合五机制检查清单,全见 `references/expert-knowledge-extraction.md`。

### 🚦 阶段二 Go / Hold / No-Go

- **GO:** 关键老员工从"被替代焦虑"转为"传承功臣"认同,愿意每周投入 2-3 小时配合;已识别并替他干掉 ≥ 1 项痛点杂活。
- **HOLD:** 中立观望。补救:加码荣誉绑定(冠名 + 汇报露脸),先兑现一个甜头。
- **NO-GO:** 公开或隐蔽抵制,关键隐性知识持有者拒绝配合。处置:必须升级到管理层重新分配利益,或重构方案绕开该卡点——不要硬推。

> **避坑:** 不要把"配合"当成理所当然。隐性知识的持有者,是这个项目真正的"数据基础设施",待遇要按基础设施来给。

## 阶段三:模型与 MLOps 并行架构(Engineering & MLOps Pipeline)

**目标:** 搭建让 AI 在生产环境活下去的骨架。这个骨架必须和模型代码**从第一天起并行建立**,不是"模型做好再说"。

### 生产架构观:控制面 vs 执行面 + 别过早多 agent 化

在划人机边界、搭 MLOps 骨架之前,先做一个更上层的架构判断——**把系统拆成两层**:

- **控制面:** 计划、路由、策略、评估、版本管理、人工介入门控(决定"该走哪条流程、用哪个模型版本、要不要拦下来审")。
- **执行面:** 检索、特征读取、模型推理、工具调用、事务落地(老老实实干活,全程可观测可审计)。

agent 在生产里不是"对话循环",而是**需要状态机、审计轨迹、审批门控的应用运行时**。把控制逻辑和执行逻辑混在一个"超级 agent"里,是后期不可治理的根源——改路由要重发 agent、加审批门要改代码、出事定位不到哪一层。禁区(审批门 / kill switch / 置信度门)必须挂在控制面上,才拦得住执行面。

**另一个高频坑:过早多 agent 化。** 别一上来就搭层层 agent hierarchy(觉得"多 agent = 更先进")。Klarna 用**单 agent + 极强路由 + 强检索**扛起 230 万次对话/月、三分之二客服量——复杂度优先放路由与流程建模,不要优先放 agent 数量。只有当问题天然可分解、工具上下文过宽、或多并行子任务明显增益时,才上多 agent;默认起点是单 agent + 强路由,先把 agent 工作流当 graph 画清楚。

还有一条底层理论:真正的 AI/ML 生产系统同时承受**代码、数据、模型**三条变化轴(CD4ML),必须作为可重复发布的工件一起管——这就是为什么下面的 MLOps 六大骨架不是"锦上添花"而是"不搭就死"。Google《Hidden Technical Debt in ML Systems》点破:ML 系统大头难度不在模型,在耦合、依赖、反馈回路和不可见技术债。

> 控制面/执行面拆分检查点、单/多 agent 决策清单、code/data/model 三轴、KPI 四层、部署三问、error budget、三个真实案例(Morgan Stanley/Klarna/Uber)、合规扩展(NIST AI RMF / SLSA / EU AI Act 时间线)见 `references/production-architecture.md`。

### Decision OS 视角:从"会回答"到"进业务闭环"

控制面/执行面回答"系统怎么拆";但还有一个更上层的问题:**这个 AI 是只想"回答问题",还是要"进入业务闭环、参与决策、推动处置"?** 后者是一类完全不同的交付,它要求在架构之上再建一层"业务语义 + 决策闭环"。

用六层闭环(Sense 感知 → Understand 理解 → Reason 推理 → Decide 决策 → Act 执行 → Learn 复盘)定位交付范围,并评估五大支柱是否齐备:

- **Ontology 业务语义层** —— 对象/属性/关系/规则/动作是否被系统化统一定义(AI 进入责任链的前提);
- **数据→本体映射** —— 表、文档、图表能否绑定到业务对象、成为可追溯证据;
- **GraphRAG Evidence Package** —— 从"检索文本"升级为"沿对象关系组织证据";
- **受控 Agent** —— 自治等级 L0-L3 显式标注,默认从 L1(起草待审)起步;
- **可治理 Action + Decision Object** —— AI 结论沉淀为带 evidenceRefs/rulesMatched/traceId 的可治理对象,Action 走 Propose→Approve→Execute→Audit→Rollback 生命周期。

**对 Go/No-Go 的含义:** 若客户诉求是 L4-L5(决策闭环)却没规划 Ontology 与 Decision Object,记为架构 Hold——模型再强也进不了责任链。若诉求只是 L1-L2(看板/问答),别过度设计,轻量 RAG 即可。

> 五大支柱的实操拆解(Ontology 成熟度评估表 / Evidence Package 与 Decision Object schema / Action 生命周期元数据 / 自治等级 / 行业 Pack / 三个真实案例:发票催收·油田井控·数据治理)见 `references/decision-os-playbook.md`。

### 人机边界明晰化(架构层留接口)

把系统决策分三类,在架构层分别处理:

| 类别 | 定义 | 处理 |
|---|---|---|
| **A 类:完全自动** | 低风险、易挽回(归档、标签、初筛、分诊) | AI 直接执行,留日志 |
| **B 类:AI 建议 + 人工审核** | 核心价值区(诊断、审批、定价、质检) | 预留审核接口、可追溯、可一键驳回 |
| **C 类:AI 禁区** | 高风险、不可逆(签约、放款、手术、处罚) | 纯人工,AI 最多提供参考信息 |

把价值最大的 B 类做大、做扎实,是 B 端 AI 的胜负手。审核接口要预留,且全程可追溯(谁审的、改了什么、为什么),这是合规与信任的基础。

**但光"留个审核接口、放个人"远远不够。** 下面三条禁区线,是把 A/B/C 边界从"画在 PPT 上"变成"真能在生产里兜住底"的关键深化——它们回答的是 AI 的**决策权、审核的有效性、agent 的权限边界**这三件最容易翻车的事。

#### 第一条线:不可逆决策,AI 不能有最终决定权(深化 C 类)

C 类之所以是"禁区"而不只是"低权重",根源在于 AI 天生有概率出错,而且错的时候**特别自信、特别像那么回事**——一个会一本正经胡说八道的东西,可以干很多活,但不能把"错一次就完蛋"的事交给它拍板。判断标准只有一句:**这条决策错了,能不能挽回?代价你扛得起吗?** 不能的,就是 AI 禁区。AI 可以把材料和依据备齐、排好候选方案,但**那一锤子必须人落**——架构上,这类操作 AI 永远只能输出"建议",落锤的执行权物理上不在它手里。

#### 第二条线:"加个人来审核"是虚假安全感——破自动化偏见(深化 B 类)

很多人觉得禁区好划:高风险的让 AI 做、后面加个人审一下(human in the loop)。这藏着一个致命陷阱叫**自动化偏见(automation bias)**:AI 持续靠谱地输出结果,审核人会在不知不觉中越来越信它,审核慢慢退化成橡皮图章。航空、医疗早有实证(International AI Safety Report 2026),放到 AI 上一模一样。关键认知:**审核有不有效,不取决于你放没放人,取决于你的设计逼不逼着这人真的去审。** 三招,跟人性的偷懒对着干:

1. **绝不给"一键全部通过"按钮。** 它是自动化偏见的温床,给了人就会用。给每个结论标**出处**,逼审核人必须点开、对到原始材料那一行才能通过——让"核对"从可选变必经。
2. **分级审核,防审核疲劳。** 每件事都人审,人很快疲劳就无脑通过。按风险分层:低风险的 AI 自己过、只通知一声;只有真正高风险、不可逆的才强制逐条人工。把人注意力集中砸在少数要命的决策上。
3. **给 AI 装"心虚"机制(置信度门)。** 让它对每个判断标置信度,低于阈值**自动停下、强制转人工**——让系统在最可能出错的地方主动把人拽进来,而不是等人去大海捞针捞错。

#### 第三条线:Agent 权限禁区——破"过度代理"(Excessive Agency)

以前的 AI 主要是"说"(最多说错话);现在的 agent 是"做"——调工具、动系统、发邮件、改数据、执行操作,从一张嘴变成一双**会犯错的手**。最常见的生产事故不是模型不够聪明,而是 agent 权限没划清、被允许做了本不该有权做的事,这种叫**过度代理(Excessive Agency, OWASP LLM06)**。四个打法:

1. **默认全禁,逐项授权(default deny)。** 默认什么都不准碰,再一项项明确地开。需要读 A 表就只开 A 表读权限。两个方向最坏情况天差地别:默认全禁最多少干点活,默认全开会捅个兜不住的篓子。
2. **身份化。** 给 agent 独立身份 + 严格限定的权限清单,凭证**短期过期、用完即失效**,不借管理员账号。能碰什么记在账上,出事能精确倒查是哪个 agent、用什么权限、干了什么。
3. **读写分离,破"致命三角"。** 别让一个 agent 同时:读敏感数据 + 对外发送 + 处理不可信外部输入。三角凑齐最危险(可能被 prompt injection 骗着把数据打包发给攻击者)。拆开:读敏感的没对外发送权,对外的碰不到敏感数据,一个 agent 同时只占三角里一个角。
4. **危险操作审批门 + 预算/次数熔断。** 不可逆操作(删数据/转账/对外发布)必须停下来等人批,低风险的自己跑、留记录;再加硬性的预算和次数上限,触顶自动熔断——agent 在循环里跑,一个 bug 能几分钟烧掉一大笔钱,熔断是最后一道闸。

> **原则:对 agent 来说,更紧的边界不是自主的敌人,恰恰是自主能成立的前提。** 权限收得越干净越精确,你才越敢放手让它在安全范围里自动跑;边界模糊的 agent 你根本不敢给真正自主。三条线的实操拆解(决策权分类清单 / 审核设计检查点 / Agent 权限审计清单 / 致命场景 / 起步操作 / 客户与法务话术 / 合规引用)见 `references/permissions-and-oversight.md`。

### MLOps 六大开源骨架(针对该场景起步)

1. **数据/特征版本管理** —— DVC / Feast。没有数据版本,出了问题无法复现、无法追责。
2. **实验追踪** —— MLflow。记录每次实验的超参、指标、产物,避免"上周那个效果好的模型找不回来了"。
3. **模型注册表 + 一键回滚** —— 出事时能 30 秒退回上一个稳定版本,这是生产系统的底线。
4. **流水线自动化编排** —— Prefect / ZenML。训练、评估、部署自动化,不要靠人手跑脚本。
5. **部署与金丝雀发布** —— FastAPI + Docker + K8s。先小流量灰度,确认无异常再全量。
6. **四层专属可观测性监控** —— 最容易被砍、却最不能砍的部分:
   - 基础设施层(延迟、QPS、错误率、资源)
   - 模型层(准确率、置信度分布)
   - 数据漂移层(输入分布是否偏离训练集)
   - 大模型/Agent 幻觉追踪(LLM/Agent 场景尤其要追踪幻觉、工具调用失败、死循环)

**🎯 P0 三件套(生产生命线,优先跑通):** 实验追踪(MLflow)+ 模型注册表/一键回滚 + 监控告警。这三件是 95% 项目死亡的真正原因——不是模型不够大,是没这三件基础设施。资源有限时死守这三件,P1(数据版本、流水线、部署金丝雀)尽快补,P2(特征仓库、漂移/幻觉监控)按场景补。

> 每个组件的实操拆解(合格检查点 / 致命场景 / 起步操作 / P0-P2 优先级 / 四层监控工具栈)见 `references/mlops-playbook.md`。

### 🚦 阶段三 Go / Hold / No-Go

- **GO(可上生产):** A/B/C 边界已定义并留接口 + 六大骨架中至少【数据版本 + 实验追踪 + 监控 + 回滚】已落地 + 金丝雀发布通道就绪 + **B 类审核已做防自动化偏见设计(禁一键通过 / 分级 / 置信度门)+ 涉及 agent 时已配:默认全禁逐项授权、身份化、读写分离、审批门与预算熔断**。
- **HOLD(只能内部试点,禁对外):** 仅有模型 demo,MLOps 未建,或权限/审核边界尚未设计。这是绝大多数 PoC 的真实状态——可以在内部跑,绝不能对客户称"上线"。
- **NO-GO(红线):** ① 跳过监控与回滚、直接把 demo 推到真实业务流;② **C 类不可逆决策交给 AI 拍板**;③ **Agent 默认全开 / 借用管理员权限跑生产(过度代理)**。任一都会出事不可挽回,且一次性摧毁客户对 AI 的全部信任。

> **避坑:** 监控(尤其数据漂移和幻觉追踪)是客户砍预算时第一个想删的,也是出事时唯一能救命的。合同里就把监控列为不可删项。同理,**agent 权限和审核防自动化偏见设计,也是"砍预算时最先被简化、出事时唯一能救命"的东西**——别让客户以"先跑起来再说"为由把禁区拆掉。

## 阶段四:挺过第 35 天"试点疲劳"(Expectation Management)

**目标:** 用专业沟通与节奏,对抗项目最容易死掉的"信心崩塌期"。技术做对了,但客户在第 35 天失去信心,项目照样死。

### 节奏总纲:land-and-expand(土地换和平)

预期管理的根本手段不是话术,是**交付节奏**——做贪吃蛇,不做瀑布。闷头做三个月再上线,项目大概率死在第六周(甲方看不到东西就怀疑、抽人、砍预算)。Palantir 驻场靠的不是季度末惊喜,而是**土地换和平**:

- **第 2-3 周必须交出一个能用的薄切片** —— 选一个范围极窄、专家每天都被烦、判据相对清晰的子环节,先跑通、上线、出数,哪怕只覆盖专家 10% 的工作。
- **薄切片的作用不是产生价值,是买时间和信任** —— 甲方看到东西动了,就愿意再给两个月。
- **每两周滚动交付一个新切片** —— 把一个季度的大重构,拆成 6-7 个两周的小胜利。观察期/迭代期不是开发之后的独立阶段,而是**和交付并行**(上线切片本身就是观察数据来源)。
- **薄切片一半给甲方信号,一半破专家抵触** —— 第一个切片去替专家干脏活(配合机制 3),用即时好处把一个理性上该防着你的人,一步步变成配合你的人。节奏和政治是耦合的。

**选第一个薄切片的优先序:** ① 窄(范围小到 2-3 周能跑通)② 烦(专家每天都被它困扰,干了能立刻换信任)③ 判据清晰(成功标准好量化)④ **不碰核心机密判断**(别一上来就奔着专家最不可替代的逻辑去)。四条都满足的子环节,就是第一个薄切片。

### 四大动作

**① 启动会预防针机制**
在项目启动会,就提前告知管理层:前 30 天是水面上的 40%(看得见的 demo 进展),之后会进入"水面下 60%"的脏活累活(集成、可靠性、合规、数据清洗)——这段时间**看起来没进展,但决定生死**。提前打预防针,好过事后解释。

**② "不性感"里程碑捞出计划**
在水面下的慢周期,刻意设计可展示给客户的务实进展:数据管道调通、监控告警上线、回滚演练成功、漂移检测报告。这些不性感,但能证明"团队在扎实推进"。

**③ 两周小步快跑验收**
把漫长最终目标切碎成**两周一次**、外行也能看懂、能签字确认的脚印。每两周一个可验收的小交付,持续制造"在前进"的感知。

**④ 反向承诺底线**
卡点暴露时,用"坦诚的现状 + 清晰的应对计划 + 明确的下一步时间"代替"下周就好"的虚假承诺。虚假承诺一次,信任清零;坦诚一次,反而赢得专业尊重。

### 商业证据阶梯:客户说好到底证明了什么

预期管理解决"客户耐心从期待转为焦虑";但还有一条贯穿全程的验证标尺——**客户说"挺好"到底证明了什么**。一句"挺好的"可能是真认可,也可能只是礼貌。可靠的判断是看客户愿不愿意承担越来越真实的成本:

```
称赞("挺厉害") → 继续聊 → 给真实材料(信任成本) → 让真实用户使用(组织成本)
→ 支付第一次费用(金钱成本) → 复购/扩展/转介绍 → 可核验的经营改善
```

证据越往上,客户承担的成本越高。**最容易犯的错是跨级替自己庆祝**:愿意给材料 ≠ 已采用,使用一次 ≠ 持续使用,付过一次钱 ≠ 已续费,更 ≠ 经营结果已提升。第 35 天 HOLD 时,把当前已到达的最高证据层级摆到台面,比"功能又多了几个"更能稳住决策者。完整七层、采用四道门诊断、价值分配(先让客户得 100 再拿 5)、反面案例(收过钱却没长成产品)见 `references/field-to-cashbox-playbook.md`。

### 🚦 阶段四 Go / Hold / No-Go

- **GO(项目续命):** 管理层接受"水面下 60%"的现实 + 两周节奏验收已建立 + 有可见的不性感里程碑。
- **HOLD(预警):** 管理层开始催"怎么还没效果 / 别人家都上线了"。处置:立即启动预期管理话术,把一个已完成的不性感里程碑摆到台面。
- **NO-GO(崩盘边缘):** 客户要求虚假承诺("下周必须出效果")或已出现信任崩塌信号。处置:触发反向承诺底线,必要时把成功标准与 Plan B 重新摆到桌面重新对齐,而不是硬撑。

> **避坑:** 第 35 天不是日历上的某一天,而是"客户耐心从期待转为焦虑"的那个心理拐点。FDE 的嗅觉要能在它到来前一周就开始拉响预期管理。

## 调用本技能时的输出格式

当用户给出一个【具体业务场景/行业】时,按以下结构产出:

1. **【场景痛点诊断】** —— 一句话点破这个场景落地最难的"人际瞎火点 + 工程瞎火点"。
2. **【交付任务看板】** —— HTML 表格,列:`阶段 / 具体核心任务 / 交付动作或话术 / 避坑警示`。
3. **【四阶段 Go/No-Go 评估总表】** —— 该场景在每个关卡的判定(绿/黄/红)+ 理由。
4. **【关键交付话术卡】** —— 2 段核心话术:对老员工的"传承话术"、第 35 天对老板的"预期管理话术"。
5. **【权限与人工监督设计】** —— 该场景的:不可逆决策清单(C 类禁区,只建议不拍板)、B 类审核的防自动化偏见设计(分级 + 置信度门 + 出处强制核对)、若涉及 agent 的权限边界(默认全禁的最小权限清单 + 是否存在致命三角风险 + 审批门与熔断阈值)。
6. **【生产架构与 KPI 锚点】** —— 该场景的:控制面/执行面怎么拆、默认该用单 agent 还是多 agent(给理由)、code/data/model 三轴当前状态、KPI 四层里哪些可立即量化锁定、部署三问的初步答案(部署在哪 / 状态谁握 / 发布谁控)。详见 `references/production-architecture.md`。
7. **【决策闭环范围与可治理产物锚点】** —— 该场景用六层闭环定位交付落在第几层(Sense→Act,工期量级随之而定)+ Ontology 成熟度现处 L0-L3 哪级 + 核心业务对象/关系/规则清单 + Agent 自治等级建议(默认 L1)+ 若进入 Decide/Act 层:Decision Object 与可治理 Action 生命周期怎么设计(幂等/审批/回滚补偿)。详见 `references/decision-os-playbook.md`。
8. **【专家知识抽取与配合策略锚点】** —— 该场景的:核心专家是哪一型(职业荣誉型/打工型/防御型/濒临退休型)→ 阶段二先出哪张配合牌(五种机制里选);隐性知识抽取计划(用哪几种手法:影随 think-aloud / CDM / 对比反例 + 重点解压缩的黑话清单);专家的隐性判据抽出来后落成什么形态的决策树(触发/判据/动作/例外,例外条款预估几条);第一个 land-and-expand 薄切片选哪个子环节(窄/烦/判据清晰/不碰核心机密);如何避免单点依赖(横向交叉验证的专家数)。详见 `references/expert-knowledge-extraction.md`。

9. **【商业证据层级判断】** —— 该场景当前已到达商业证据阶梯的哪一层(称赞/继续聊/给材料/真实使用/首次付费/复购/经营改善)、对应的真实行为证据是什么、还缺哪一层、下一轮只提一个强度匹配的请求(再给材料/让第二位用户试/连续使用/小额内测费/正式合作)。不跨级庆祝,不用低层证据替代高层结论。详见 `references/field-to-cashbox-playbook.md`。
10. **【产品化沉淀建议】** —— 该场景若已发生两次以上真实交付:把重复基础/客户特例/人工责任分成三堆,当前最轻的沉淀载体是什么(SOP/模板/Prompt/Skill/Agent/产品模块),处在 0→1/1→10/10→100 哪道门,下一轮只验证哪一件事。若只发生过一次,明确标注"尚未到产品化阶段,先补第二次真实交付"。详见 `references/field-to-cashbox-playbook.md`。

完整可量化打分表(带权重、分数阈值、决策矩阵)与更多话术变体见 `references/scorecard.md`。

## 执行手索引(评估出锚点后,调谁干活)

本 skill 是**判断层**(设计图:该不该做、怎么做对、卡在哪);下面这些已装进 `~/.claude/agents/` 的执行 agent 是**施工队**——跑完四阶段、锚出缺口后,按缺口调对应执行手把那一步**干出来**。它们只执行,不替你做"该不该做"的判断。

| skill 的环节 / 锚点 | 调用执行手(`~/.claude/agents/`) | 它干什么(执行,非判断) |
|---|---|---|
| 阶段一 · 真需求卡 / 锁交付范围(第五维) | `specialized-workflow-architect` | 把客户业务全路径(含分支/失败/回滚/交接)画成 build-ready 流程树 |
| 现场到钱箱 · 售前 POC / 技术演示 | `sales-engineer` | 技术发现、Demo 工程、POC 范围、竞品 battlecard |
| 阶段三 · 生产架构 / 集成骨架 | `engineering-backend-architect` | API 设计、数据架构、系统集成方案 |
| 阶段三 · 权限禁区(A/B/C + Agent 权限四打法) | `engineering-identity-access-engineer` | SSO/SAML/OIDC/RBAC、最小权限落地 |
| 阶段三 · Decision OS 的 Evidence / RAG | `engineering-rag-pipeline-engineer` | chunking / 检索 / 重排 / eval 的生产 RAG 管道 |
| 阶段三 Go/No-Go · 上线质量门 | `testing-reality-checker` | 证据驱动的生产就绪认证 |

> **调用纪律(与核心铁律一致):**
> - **先 skill 后 agent。** 永远先跑四阶段 Go/No-Go,GO 之后再调执行手;别让执行手替你做"该不该做"的判断。
> - **做窄做深,一次 1-2 个。** 按当前薄切片最缺的那一步调对应执行手,别一次拉一整队(呼应核心铁律"做窄做深"和"复杂度优先放路由,不堆 agent 数")。
> - **禁区由 skill 划、执行手施工。** "哪些是 C 类禁区 / Agent 自治到几级"的判断权在 skill(`references/permissions-and-oversight.md`、`references/decision-os-playbook.md`),Identity Engineer 只负责把它落成代码。
> - **质量门由 Reality Checker 出证据、scorecard 出判定。** 执行手产出证据,过不过关由本 skill 的量化打分表(`references/scorecard.md`)判定,不由执行手自评。

> **交付后运营阶段(激活 / 续约 / 扩收 / 规模化):** 当前主要靠对应 reference 的方法论 + FDE 现场自判,**暂无专用执行手**。涉及具体技术施工时仍调上方对应执行手——例如激活期的集成战役调 `engineering-backend-architect` / `engineering-rag-pipeline-engineer`,上线质量门调 `testing-reality-checker`;续约 / 扩收 / 规模化的打法手册沉淀、组件库抽象,本质是 `decision-os-playbook.md` 的 Ontology / Decision Object 工作,可调 `engineering-rag-pipeline-engineer` 配合。**指标体系(`fde-metrics.md`)的搭设是 FDE 自判 + 业务方共建,不外包给执行手。**

## 核心话术卡(内置 2 段)

**① 对一线老师傅的"传承话术"(开场定调,严禁"替代"):**

> "X 师傅,我们这次来,不是要替代您,恰恰相反——您的手艺是咱们厂的命根子,可这套东西在您脑子里,没沉淀下来。我们想做的,是把您几十年的经验抢救出来、存下来、传下去,让徒弟们都能学到,也让您不用再把时间耗在那些填表抄录的破事上。这个系统,我们想以您的名字命名,叫'X 师傅经验模型',您来当总顾问,把关、署名。它将来准不准,全靠您。"

**② 第 35 天对老板的"预期管理话术":**

> "X 总,前一个月您看到的 demo 是水面上的 40%,快、看得见。从现在起,我们进入水面下的 60%——集成、可靠性、合规、数据清洗,这些活不性感,但这段时间的扎实程度,决定这个系统能不能真的扛住您每天的业务、出事能不能兜得住。我每两周给您一个能验收的小节点(数据管道调通、监控上线、回滚演练),让您清楚看到我们在稳步推进。中间如果遇到卡点,我会第一时间告诉您现状和应对计划,绝不给您'下周就好'的空头支票。我们要的不是快,是它真的能跑、能扛、能信。"
